# 灵鲸插件底座独立评审（Codex / gpt-6-astra）

## ① 总评

**方向成立，但当前三稿尚不能直接作为完整实现 spec。** 可以开始 Cordis 封装验证与 m0 最小链路；并行开发各插件前，应先修正下面五项阻塞问题，否则不同实现者会自行补出互不兼容的机制。

最重要的三条意见：

1. **先把“同一契约支持进程内外”落实为真正的消息协议。** 当前存在会话对象、同步返回值、Zod 实例、Date、函数，无法按现有规则自动生成 IPC 代理。
2. **required 不可替换与调用权限必须分别落实。** 禁止替换插件，并不能阻止插件直接调用 `slots.bind`、原始大脑、投递器、账本主人接口。信任等级也不能由包自行声明。
3. **把装配、初始化、恢复、开放业务分阶段。** “所有 required ACTIVE”不等于系统可用；“全部 core 永远 required”又会让 m0 被尚未开发的模块拖住。

## ② 问题清单

**01｜阻塞｜“一切可序列化”与第一批接口不相容**

位置：C §2、§5.0–§5.6、§7；K §8.3。`createSession()` 返回带方法的 `BrainSession`；`describe`、`rank`、`renderPersona` 等同步返回，IPC 调用却必然异步；`JobTrigger.schema` 是 Zod 实例；引用的 `05-memory.md` 中 `forget` 接收 Date，`MindContext` 包含函数和 Date。这不是补 schema 就能解决的差异。

建议：明确分开 **wire DTO、方法描述、本地便利接口**。wire 层统一对象参数、JSON 返回值与异步调用；创建会话返回 `sessionId`，后续请求携带该句柄及进程代际。若保留对象式门面，明确句柄包装、销毁与静态元数据缓存规则；不可远程化的纯函数明确标为本地能力。

**02｜阻塞｜Zod 4 的枚举 record 会拒绝文档里的正常配置**

位置：C §3。若采用 Zod 4，`z.record(SlotName, value)` 会要求枚举中的全部键存在。因此只提供 `brain.provider` 的 manifest、只绑定三个槽位的成员配置都会失败；外层 `.optional()` 只允许整个字段缺省，不能让其中的键变成可选。

建议：钉死 Zod 版本；这些稀疏映射改成 `z.partialRecord(SlotName, value)`，必要槽位由计划校验负责。把 K §3、§4 的完整示例作为必须通过的 schema 样例，避免只测坏值。

**03｜阻塞｜信任等级及 required 身份仍可由被加载者自报**

位置：K §2、§3.1、§5、§10。任意包可声明 `kind: builtin`，external 又允许显式 `process: in`；required 的资格只写了包名限制。包名、插件 id、manifest 都不是可信来源证明，初始 profile 也不应成为绕过 patch 禁令的入口。

建议：由发行版内置表和主人安装记录决定来源、允许进程模式及权限；manifest 只能提出需求。required 固定到可信解析位置、入口及发行版身份，profile 只能配置允许字段，不能重定向其代码。所有配置层都应用同一不可替换校验。

**04｜阻塞｜公共 API 暴露了绕开行动管线和主人权限的路径**

位置：K §6.2、§9；C §7。所有插件得到完整 `Slots`，其中有 `bind`、`define`、任意 `resolve`；插件可解析原始 `form.adapter.deliver`、`brain.provider.createSession`、收费能力。`consumes` 只检查服务名称，也未阻止获得 `journal.append`、出生设定修改或主人搜索接口。`inject` 是依赖声明，不是授权。

建议：拆出宿主管理接口、插件注册接口、受限消费接口；`bind/define` 仅宿主可用。原始执行器只交给对应 required 编排服务；插件通过受授权的查询、提案或行动接口访问。主人操作另设入口，由 gateway 验证后的宿主能力调用，不接受插件自报 `by:'owner'`。构造真实的受限门面，不能只给 Cordis ctx 换一个 TS 类型。

**05｜阻塞｜启动成功条件不足，且 m0 与“全部 core required”冲突**

位置：K §4.1、§5、§12；C §5.2；E §4.7。计划阶段有实现不代表运行时成功注册；builtin 初始化失败后仅禁用，却可能留下必须存在的记忆引擎。required 全部 ACTIVE 也不能证明已完成日志恢复、孤儿清理和投影追赶。全部 core 自动补齐还意味着 m0 必须先实现整套编排与账本。

建议：由可信发行版定义各阶段的必需模块集合，禁止 patch 削减；m0 只包含其完整安全链路。启动分为计划校验、注册初始化、恢复、运行时槽位校验、开放业务；必需槽位缺失必须失败，可选能力才降级。`apply` 不得提前接消息、启动业务作业或对外行动。

**06｜重要｜Cordis 生命周期有三处不能按概述直接实现**

位置：K §3.2、§5–§7、§13。缓存源码中：`registry.plugin()` 返回可等待的 fiber，但 `fiber.await()` 只等当前 `inertia`，可返回 PENDING；`_unload()` 对顶层清理使用 `Promise.all`，虽然逆序发起，却不是严格串行完成；`emit()` 同步调用监听器，不捕获异常，也不等待异步监听器。另有 `defineService` 接受异步工厂，但说明直接 `provide(key, factory(ctx))` 会注册 Promise。

建议：显式观察状态和就绪条件；工厂先 `await` 再发布服务。若承诺严格 LIFO 清理，由 kernel 自建串行释放栈。生命周期通知统一处理监听器错误和拒绝，required 故障策略不能只依靠“未捕获异常”。启动总期限从导入前开始，失败时清理已装载模块；同进程同步死循环无法靠普通计时器中断，应明确这个边界。

**07｜重要｜Standard Schema 支持不等于任意 Zod 配置可导出**

位置：K §0、§3、§5；C §0、§12。Cordis `resolveConfig()` 调用 `Config['~standard'].validate()`，明确拒绝异步校验。自定义 transform/refine 等规则也不能保证等价导出 JSON Schema。目前配置实际校验被放到导入后，进程外插件又不能靠宿主导入其 Config 完成校验。

建议：规定可导出的 schema 子集、JSON Schema 方言、默认值及输入输出模式；禁止异步 Config 和不可导出的 wire 转换。生成的 schema 是构建产物，不承诺判断任意两份 schema 的语义等价。导入前按该产物校验配置，导入后检查产物一致性；补明运行时 JSON Schema 校验器及其依赖归属。

**08｜重要｜kernel 与 core 的装配责任没有闭合**

位置：K §5、§9；E §4.2–§4.3。kernel 要读取 core 的 required 清单和层表、调用 core 的 procs，但依赖规则禁止 kernel 依赖 core；`startKernel` 又没有接收这些描述或能力的参数。`core/app` 同时负责读 profile、启动顺序，与 kernel loader 重叠。

建议：确定 `core/app` 为组合入口，向 kernel 传入可信 required 描述、启动策略及 bootstrap 接口；kernel 只实现通用装配算法。procs 等基础服务就绪后才能启动进程外插件。E §4.3 删除重复 loader 职责，写明正常启动和测试共用的入口。

**09｜重要｜manifest 尚不能完整描述一包多插件和进程外入口**

位置：K §3；C §3；E §4.2。顶层必填 `id/kind` 与 `plugins[]` 的身份、继承规则未定义；子项缺 Config、平台、进程等字段。进程外 `spawn` 使用的 `cmd/args` 没有来源，`包名#插件id` 的解析规则也未落下。

建议：定义 package 描述与 plugin 描述的规范化结果；明确子项继承、覆盖、唯一性和入口解析。TS 进程外插件可统一由宿主 runner 在子进程内导入入口；非 TS 插件另设受约束的可执行文件与 argv 描述。入口、schema、NOTICE 路径都相对已解析包根，校验真实路径及越界，不拼 shell 命令。

**10｜重要｜配置层级、成员配置和密钥只有顺序，没有完整语义**

位置：K §4、§10；C §3。未规定 extends 环、父子同 id 合并、重复 insert、缺失目标、replace 缺省字段及重新启用方式。成员绑定只有 impl，无法表达同一提供方不同模型配置；插件 `config.model` 与 `SessionConfig.model` 的优先级不明。“主人配置事件最后覆盖”又要求在 journal 启动前取得事实来源。

建议：给每种操作明确前置条件、失败语义和配置归属；定义系统默认→插件实例→成员/角色→会话允许覆盖的层级。主人绑定由其账本持有，宿主只投影应用；启动和 `dump-config` 共用可信配置读取接口。加入 `SecretRef`、解析时点及接收方授权，计划输出和装配哈希使用引用与版本，不含密钥值。

**11｜重要｜槽位计划缺少声明与实际注册的一致性检查**

位置：K §5–§6；C §3–§4。manifest 每槽位只容纳一个 impl，但 `job-triggers` 要提供多个触发类型；registry 的 key 未进入 manifest，却要求导入前去重。`single` 在流程表是“最多一个”，定义表是“恰好一个”。实际注册未要求与 manifest 对齐，缓存失效也不能撤销消费方已保存的裸实例。

建议：把贡献声明规范化为可枚举条目，明确 impl、key、顺序和允许作用域；就绪前核对实际注册集合。分开必需性与基数，逐角色规定是否允许 null。返回带代际检查的句柄或代理；提供方失效后旧引用也必须失败。工厂实例明确成员删除、初始化失败和卸载时的释放协议。

**12｜重要｜IPC 握手鉴权叙述不成立，反向调用授权缺失**

位置：K §8.1–§8.2；C §7、§10。宿主发送 token，welcome 却没有证明字段，无法执行所写的“再校验 token”。私有 stdio 已连接到宿主拉起的子进程，握手 token 本身不限制它能调用什么。插件请求宿主查账本的反向方法、schema、授权上下文尚不存在。

建议：先定义握手状态机及请求/响应方向；比较安装时固定的身份和声明，不信子进程重报的 manifest/pid。反向 RPC 只暴露明确白名单，由宿主连接绑定插件、代际、成员和当前授权范围；不接受插件自报受众或主人身份。BlobRef 只是引用，取 blob 仍需同样授权。

**13｜重要｜进程隔离、资源限制和取消尚未形成真实边界**

位置：K §8、§10；C §10。隐藏数据库路径、清洗环境、独立 cwd 都不能阻止同用户进程读取数据库或联网。64 个在途请求之后无限排队仍会耗尽内存；256 条 ACK 没有序号、字节窗口、队列上限及违约处理。取消只针对 stream，不能取消普通收费请求；永久会话事件流空闲 60 秒即超时也不合理。

建议：明确当前只做故障隔离，未经审阅代码在 OS 隔离验证前不得加载。定义队列、流、缓冲字节、日志和进程资源预算；超限拒绝或终止。取消覆盖 requestId/streamId，要求停止底层工作、丢弃晚到结果，必要时杀进程；订阅保活与活动请求超时分开。

**14｜重要｜JSON-RPC 与业务错误需要可执行定义**

位置：K §8.2；C §9–§11。C 的响应和通知简写缺 `jsonrpc`；成功/失败互斥、id 类型、无效消息、批处理策略尚未定义。“灵鲸段从 -32000 起”没有明确范围；业务字符串 code 在 IPC 映射中丢失。超时统一可重试，可能重复执行已经发生的副作用。

建议：完整定义 JSON-RPC schema 和错误码表：标准错误、`-32099…-32000` 服务端错误及应用码的分工；`data` 保留业务 code。加入取消及执行结果不明语义，区分“可重试故障”和“此动作可安全重试”；请求 id 不替代持久幂等键。前后端 Response 改为按 `ok` 区分的互斥联合。

**15｜重要｜大脑契约缺少可记录、可恢复的事件状态机**

位置：C §5.1；E §4.8。两个回合之间崩溃没有当前 turnId，却必须发送带 turnId 的 `turn.failed`；缺中断终态。消息无 itemId，增量或全量含义不明；权限请求缺回合绑定。usage 允许 `none/quota`，结束事件却要求 token 和推理次数。原生工具只有定义，没有调用和结果回传桥；第一批工具收尾能力也没入契约。

建议：补 session/turn/item 状态与终态唯一性、订阅建立顺序、晚到事件处理、权限失效规则；空闲崩溃用会话级错误。Usage 使用显式计量联合，未知值不得伪填 0，由 guard 决定是否准入。补工具执行桥、批次边界及能力不足时的降级规则；只有完成条目进入经历流。

**16｜重要｜时钟与随机源不能满足已定回放要求**

位置：K §9；E §4.3；对照 overall §3.1、§6.8。`Clock` 只有 ISO `now()` 与 timer，缺单调时间；随机源只有导出 state，没有恢复协议、算法版本或 fork 命名规则。共享 RNG 的调用顺序还可能随插件装载变化而改变身体轨迹。

建议：分离挂钟、单调时钟和可控定时器，明确时区、休眠跳变及同刻事件顺序。随机源按成员和用途稳定分流，支持版本化恢复。装配变动不得扰动 body 的随机序列；日志记录回放需要的配置、时钟及随机源版本。

**17｜重要｜事件信封已写，追加与重建的关键协议仍空缺**

位置：C §6–§7。`Journal` 只有名称，没有区分追加请求与已提交信封；谁生成 pos/seq/actor/source 没写。overall 要求的 expectedSeq、同事务投影与幂等约束未进入本稿。不可变信封中的 `payloadRef.erased` 又无法反映之后的删除。

建议：补最小 `AppendRequest/CommittedEvent`、冲突返回、订阅游标、投影注册与检查点协议。pos/seq 由 journal 生成，来源及受众由可信所有者提供；插件不能提交任意完整信封。删除状态放载荷读取结果或删除事件，不修改历史信封。规范生命周期信号到 `kernel.*.v1` 持久事件的映射。

**18｜重要｜版本体系漏了宿主 API，事件迁移策略也相互矛盾**

位置：C §12；K §3、§8；E §4.2。槽位版本无法覆盖 KernelContext、账本 API 的变化；只实现相同槽位版本的插件仍可能调用不存在的宿主 API。前后端和 IPC 共用版本号造成无关联动。C 要保留旧事件 schema 重放，overall §12.8 则规定一次性迁移、不保留版本分支。

建议：增加宿主 SDK/API 兼容声明与导入前校验；前后端、插件 IPC 分开版本，仍可统一发布。明确事件采用哪一种已批准策略，旧 schema 留在迁移工具还是常驻运行时。装配记录包含解析后的包版本、内容摘要、配置版本与契约版本，不能只记录包名。

**19｜重要｜算法契约没有表达其实际交互需求**

位置：C §5.3、§5.5；`05-memory.md` §3.5。`proposeGrowth` 注释说返回“要问什么”，类型却只返回最终提案；记忆引擎需要 minds 代问，但调用阶段不明确。`JobTrigger.next(spec, now, {lastRunAt})` 能表达时间触发，不能单独实现事件触发、空闲触发。

建议：定义“准备输入与输出 schema→minds 执行→解释结果/交提案”的分阶段契约，禁止引擎自行启动无监管 CLI。触发器拆时间计算与事件/状态匹配，scheduler 持有订阅和作业状态；或者首版只开放时间触发器，其余先由内核编排。

**20｜重要｜插件派生状态与 worker 执行没有接缝**

位置：K §6.3、§9；E §4.3、§4.7；对照 D3、`05-memory.md` §7.2。规定引擎只能把派生数据放 derived.db，却没有可用的存储能力；又禁止依赖 core。记忆排序要求在 worker 运行，但注册的是主线程实例，方法和闭包不能直接传给 worker。

建议：明确哪些索引由 core 投影器统一持有，哪些允许插件私有派生状态。后者通过带插件、成员、版本命名空间的宿主接口访问，包含重建水位和删除级联。worker 使用可加载纯函数入口或消息服务，不能传运行时实例。共享实例缓存必须按成员及授权范围隔离。

**21｜重要｜保护出生账本不等于保护每次注入的人设**

位置：C §5.3–§5.4；对照 D1、D3、D4。成长插件拿到 birth 后返回整段任意文本，能省略或替换实际注入的出生设定；关系插件返回内核词表里的权限，也不代表这些权限已获主人授权。这是调研边界本身尚未落实的风险。

建议：不可变人设锚由 required 的 self/context 从账本直接生成并装配；成长插件只返回明确的可替换段落与提案。角色默认权限仅在主人接受模板或配置时生效，运行时只能在已批准上限内计算，不能因为插件升级静默扩权。

**22｜重要｜模块落位与整体架构的依赖方向冲突**

位置：E §4.6–§4.7及引用的 §5；overall §3.2。E 把账本写成引擎槽位消费者，overall 却明确“账本不知道引擎是谁”；E 的编排/运行层次序与 overall 相反，context 的层归属也不同。照任一层表写依赖检查，都会阻止另一份文档要求的调用。

建议：区分账本校验器与业务门面/编排器，后者解析引擎，再把结果交账本。统一一张实际调用图，允许必要的同层公开接口，但禁止环；订阅和回调方向单独画清。工程层表由这张图派生。

**23｜建议｜仓库约定与未来插件类型需要消除机械冲突**

位置：E §4.1–§4.6；K §2–§3；C §4。E 禁默认导出，K 却强制默认插件入口；kernel 的依赖表一处含 yaml、一处不含。UI 有 keyed/会话作用域，但 kernel 的枚举不支持；纯数据内容包又被“所有插件都有代码入口”覆盖。

建议：明确插件入口的导出例外或统一改命名导出，统一依赖白名单。UI 契约与后端 Slots 分开，首版 `client` 仅允许随仓库构建的入口。预留代码包/数据包区别，内容包不导入 JS；`brain-shared` 等普通库不要求 manifest。

**24｜重要｜Paseo 落位合理，但“照搬”边界还需收紧**

位置：E §4.8；Paseo 调研 Q4、Q10。三个适配器放 `plugins/brain-*`、共享件独立成库是正确的；但共享代码仍含进程、日志、超时、会话导入等依赖，不能照搬其默认运行方式。Q10 的工具归一、结构化生成循环、流合并等摘取项也没有明确最终归属。

建议：一次固定同一上游提交，再拆三个适配器和共享件。把依赖清单逐项映射到 procs、注入时钟、kernel logger 或 contracts；SDK 自行拉进程的路径也须落实登记。工具归一归适配器/共享库，结构化用脑编排归 core/minds，CLI 历史只作续接缓存或明确的导入来源。逐项标注“不摘”的内容，避免共享库长成第二套 AgentManager。

## ③ 缺失项

以下需要在开工前补成短表或验收条目，不必另写大篇设计：

- **权限矩阵**：每类插件能注册、解析、读取、提出什么；哪些只有宿主、账本所有者和主人入口能做。特别覆盖出生设定、绑定、原始投递器、进程与 blob。
- **启动/关闭阶段表**：迁移、日志恢复、孤儿清理、投影追赶、槽位就绪、开放业务；关闭时先停新准入，再取消/排空，最后释放资源、procs 和 journal。明确总关闭期限与退出码。
- **故障维修模式**：required 无法启动时，“只起主控台”究竟依赖哪些最小能力；不得通过跳过鉴权或写入校验实现。
- **真实装载测试接缝**：`createTestKernel(plugins[])` 不能替代 manifest、包解析、入口默认导出和 Config 的集成测试。让测试包经过生产 resolver/loader，替换文件读取、进程传输等外界接缝。
- **必须覆盖的反例**：伪装 builtin/required、越权 bind/调用原始执行器、必需实现初始化失败、异步清理顺序、进程重启后旧句柄、超时但副作用已发生、跨成员缓存、删除后的派生数据、随机状态恢复。
- **可观测字段**：插件/实例/进程代际、成员、会话、回合、请求、关联号、装配版本；等待依赖、队列长度、未完成清理与降级原因。插件 stderr 需轮转、限额和脱敏，不能直接视为安全日志。

## ⑤ 可以删掉或推迟的

- **m0 不必先完成完整 IPC 宿主。** 现在先定可编码的 wire 契约，做最小子进程往返验证；完整流控、熔断和恢复随首个真实进程外能力进入验收。
- **六种基数无需一次全部实现。** 先做 m0 实际使用的绑定与注册，未来基数可以保留设计，不得以未实现行为通过 manifest 校验。
- **UI 动态贡献、第三方视图、内容包导入、安装界面继续后移。** m0 的协议只需保留清晰扩展位置。
- **插件间运行时依赖图、热重载继续不做。** 现在仍须校验 required 的依赖环，并做好释放与失效句柄；这不等于实现生态级依赖管理。
- **跨语言自动 SDK、任意同步接口透明远程化可以删去首版承诺。** 一个受限、明确的异步 RPC 协议更容易独立实现和验证。
- **保留替换演练，但缩小到机制验证。** 用第二个简单实现证明装配替换、状态重建和受众检查成立；完整记忆算法对比按既定 V1.1 安排。
- **不要推迟权限门面、必需槽位就绪检查、配置确定性、时钟随机注入和真实 loader 测试。** 这些决定后续模块的形状，后补才容易返工。

## ⑥ 需要主人拍板的

**技术错误修正无需重新拍板。** Cordis 4、钥匙串优先、第一版只装仓库插件、三类 Paseo 适配器落位，都按现有决策推进。

需要新确认的是一项交付范围调整：**是否把底座验收拆成“m0 必需机制”与“首个进程外插件必需机制”两阶段。建议拆。** m0 先验收终端收发、CLI 用脑、`reply/inner`、经历流、鉴权、暂停、恢复与真实装载；完整 IPC 和未来槽位随后增加。

外部插件开放、OS 沙箱、原生第三方 UI 等选择目前都可以不拍板；文档明确“尚不支持”，比预先承诺尚未建立的安全能力更准确。
