## 它是什么

一个 DSH 插件包（bundle），给一个 GitHub 仓库当主动的编码 agent，可选接飞书〔一手，S1 README〕。依赖 `@deepseek-ai/dsh-*` `^0.2.1-alpha.2` 与 DeepSeek 发布的 `@deepseek-ai/cordis` `4.0.5-alpha.1`；用 `cordis.patch.yml` 插入三个插件（本体、GitHub 来源、飞书来源）和两个 agent 预设（主会话的 router、执行器的 worker）〔一手，S1 `package.json`、`cordis.patch.yml`〕。核心原则："占用尽可能少的人的注意力，给出尽可能多的价值"〔一手，S1 `docs/000`〕。

## 双层结构

```
来源（GitHub、飞书）→ 触发（一条事件）→ 线程（同一个 PR / 话题的事件流）
   ├─ 有工单订阅了这个线程 → 直接送到那个工单的执行器，不经主会话（订阅直通）
   └─ 没有 → 评估：先规则准入，再由主会话的模型研判 → 接单 / 停止 / 忽略 / 未完成
                        │ 接单：建工单 + 授权（Mandate）+ 派工
                        ▼
主会话（Router，代码里叫 orchestrator）：一个常驻 DSH 会话；评估、接单派工、统一回复；工具少
   │ 派工                                    ▲ 汇报（进展 / 等待 / 就绪 / 受阻 / 失败 / 无需处理）
执行器会话（Worker）：每个工单一个 DSH 会话 + 一个目录（通常 git worktree）；不直接对人说话
```

- 主会话："全局序点、协调点和记忆"；只管任务之间的关联与分派，不拆单个任务的步骤；"甚至可以不配备 Bash"；较轻的模型往往够用〔二手，S2〕。
- 执行器：上下文互相隔离，挂完整工具，通常配最强的模型；同层不直接通信，冲突靠订阅同一线程收到同样事件来发现，少量协同由主会话中转；内部可再开子 agent，对主会话透明〔二手，S2〕。
- 规则准入在前、模型研判在后；同一线程同一时刻只跑一次评估，期间到的触发并入下一批〔一手，S1 `docs/001`〕。实验：触发从每分钟约 1 条升到约 40 条，平均批大小 1.0 → 2.8，单个决定的分摊推理时间 6.4 秒 → 1.6 秒〔二手，S2〕。
- 授权：接单时记下规则版本、范围、强度（明确 / 推断）、发起人；不可变，范围变大要开新工单；恢复已结束的工单前按当前规则重新核对〔一手，S1 `docs/001`〕。
- 并发：执行器名额有上限，另给"人的消息或状态询问"留一个额外名额，唤醒优先于新开工〔一手，S1 `docs/003`、`docs/007` DshExecutor〕。
- 执行器预设：前台命令超过 5 秒转为后台任务，人的新消息在下一步就能进来；一轮结束后后台任务最多再跑 30 分钟〔一手，S1 `docs/003`、`cordis.patch.yml`〕。
- 代码分层：`src/core` 只有领域规则、不做 I/O；Engine 是触发、线程、决定、工单、派工的唯一写入方；各调用方只拿到自己角色那一部分接口〔一手，S1 `docs/007`〕。

## 文章里的其他设计

| 设计 | 解决什么 | 原型里 | 等级 |
| --- | --- | --- | --- |
| 异步执行（start / stop，后台结果作为新事件回来） | 同步执行时会话收不到新输入；新输入在当前推理步结束后处理，不在生成中途打断 | 有（5 秒转后台）；文章称已在 DSH 实现但未默认开启 | 一手 S1；二手 S2 |
| 按渠道定输出规范（IM 单次回复不超过 100 词） | 把终端式长输出搬进群聊造成信息过载 | 有，写在提示词里 | 一手 S1 `prompts/`；二手 S2 |
| Inline & Spill、链式召回 | 上下文放多挤占窗口、放少要反复调工具 | 部分 | 二手 S2 |
| 投机执行 | 后台先试，有价值才交付 | 推断出的主动工作默认只记录不执行 | 一手 S1 `docs/000`；二手 S2 |
| 存算分离 | 设备休眠或离线 agent 就停 | 没有 | 二手 S2 |
| 外部看门狗会话（定时驱动，判断各执行器有没有实质进展、是否跑偏） | 模型绕圈、跑偏，进程存活检测抓不到 | 没有（源码与文档里搜不到） | 二手 S2；一手 S1（缺席） |

端到端实验（约 300 条消息含约 20 个任务，编码用只耗时的假工具，每种方案 5 次）：Super-agent p50 12.4 分钟、p95 15.7 分钟；带子 agent 工具的单会话、中性提示词 p95 29.5 分钟，5 次都没调用子 agent；去掉订阅直通，完成时间基本不变，主会话决定数多约 30%，读缓存 token 2323 万 → 3177 万。文章自称合成负载、仅作初步参考〔二手，S2〕。

## 和 Grok Bot 的区别

Grok Bot 是主人自己建几个有名字的长期 bot，每个负责一摊事，由人决定找哪个〔一手，S4 Cursor："Give each Bot one primary job"〕；第三方称可有一个"chief of staff"bot 管其他 bot，机制未公开〔二手，S4 i-SCOOP〕。Super-agent 对外只有一个入口，按任务临时开执行器。前者按角色切，后者按任务切。

## 对灵鲸的意义

- 灵鲸原设计（`overall.md` 修订前）已有同样的骨架：前台会话说话、手隔离干活且不对外说话、进模型前先过代码规则；差别在原设计按地方开在场、慢想按需醒，Super-agent 用一个常驻主会话。主人据此提出四层骨架：对外适配层、成员层（每个成员一个常驻总会话）、干活层、agent CLI 集成层，重的思考作为一件活派给第三层；完整设计见 `architecture/four-layers.md`（草稿）。
- 可借、尚未定的点（改 `overall.md` 时由设计 agent 评估后交主人定）：订阅直通（手开的 PR 上的评论、CI 结果直接进那只手）；授权记录与恢复时复核；外部看门狗会话；工单阶段表（主控台只列要人管的）；按批评估。
- 可直接参考的实现：在 DSH 上开多个会话、按预设建会话、往会话送消息、重启后恢复派工（S1 `src/app/sessions.ts`、`src/executor/dsh.ts`、`src/core/engine.ts`）；执行器预设的写法（S1 `cordis.patch.yml`）。灵鲸的 `dsh-base` 已改名为 `@liwa/*`、cordis 升到 rc.12，原型不能原样装，要改导入名并对齐 cordis 差异〔推理〕。
