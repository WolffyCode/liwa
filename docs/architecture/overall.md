## 0. 一页总览

### 0.1 核心思路

灵鲸的本体是一个"内核"：它持有她的全部状态和一本只追加的操作日志，但自己不思考。思考交给一个个 CLI 会话。每个会话都是她（以后也可能是朋友）在某个位置上的一次"在场"：

- **主意识**是唯一看全局、做全局决定的位置，给主人和她自己用；
- **在场分身**守着一个场合，比如某人的私聊、某个群【V2】；
- **干活分身**守着一件活；
- **内省会话**在后台整理记忆、写日记、提成长。

会话之间从不直接对话，只经过本体：下面的会话向上发简短的**通知**，进主意识的收件箱；主意识做的**全局决定**写回她的状态，再在相关会话的下一轮开头**广播**下去。会话只能**提出动作**，对外说话、派活、记承诺、写记忆都由本体执行；执行前统一过准入（一键暂停、花钱总闸、权限、受众），执行时先在日志里记"将要做"再去做。

这样安排换来三件事：

1. 换大脑、换 CLI、本体重启、会话崩溃，都不改变"她是谁"，因为她不住在任何会话里。
2. 隐私、花钱、兜底各自只有一个拦截点，因为所有动作都从同一条管线出去。
3. 成本跟着"起了多少个回合"走，而起不起回合由代码决定。

（依据：决策 4、11、12、13；papers-architecture §4、§6；companion-architectures §8）

### 0.2 总图

```
外界与时钟
  主控台 / 网页（浏览器，WebSocket）   外部平台适配器【V2】（各自独立子进程）   作业：定时 / 空闲 / 承诺到期
        │                                   │                                      │
        └───────────────────┬───────────────┴──────────────────────────────────────┘
                            ▼
本体（一个常驻 Node 进程，launchd 守护）
  ① 感知：归一成事件，先写操作日志
  ② 门控：代码判定去向，不调模型
       ├─ 主人私聊 ───────────────────────────────────▶ 主意识（突破通道，不排在通知后面）
       ├─ 别人私聊、群（群要过门控才唤醒）──▶ 在场分身【V2】─┐
       ├─ 作业触发 ──────────────────────────────────────────┤
       └─ 干活分身的里程碑 ──────────────────────────────────┤
                                                             ▼
  ③ 收件箱：合并、去重、排序（规则 + 紧急度 + 主意识的关注清单）──▶ 主意识
  ④ 主意识会话：决策；和所有会话一样，只提出动作
  ⑤ 行动管线（所有会话共用）：准入（暂停 / 总闸 / 权限 / 受众）→ 记"将要做" → 执行 → 记结果
  ⑥ 广播：全局决定写回她的状态，相关会话下一轮开头收到提醒
  ⑦ 学习：内省会话按批、按空闲、按作息从日志里抽记忆、写日记、提成长

  她的状态 ＝ 操作日志的投影：出生设定 · 成长 · 当下状态 · 作息 · 记忆 · 关系 · 承诺 · 日程 · 方针
        │
        ▼
每个活着的会话对应一个 CLI 子进程（Claude Code / Codex / 通用 ACP）：CLI 只是她的大脑和手
```

术语：**投影**是从日志算出来、方便查询的当前状态表，可以删掉重算；**WebSocket** 是浏览器和服务器之间一直开着的双向连接；**launchd** 是 macOS 自带的守护服务，进程退出会被它自动拉起。

### 0.3 八条架构原则

后面每一节的设计都是这八条在具体问题上的展开。

| # | 原则 | 含义 | 依据 |
| --- | --- | --- | --- |
| P1 | 灵魂在本体，会话可重建 | 她的一切状态由本体持有；CLI 会话只是工作记忆，随时可以丢掉、从日志重建 | 决策 4、11；product.md「核心理念」；papers-architecture §2.1（CoALA：记忆独立于 LLM）；companion-architectures §9 坑 9（Letta #2666 新会话即白板）；paseo-architecture §5 坑 1 |
| P2 | 日志是唯一事实来源 | 记忆、人格变化、看板、花费都是日志的投影；CLI 自己的转录只是续接用的缓存 | client-backend §3.2；product.md「记忆」；papers-architecture §6 F；companion-architectures §7.6 |
| P3 | 会话提出动作，本体执行动作 | 对外说话、派活、记承诺、写记忆只能经内核工具；准入、受众检查、写日志都在执行处 | companion-architectures §2.2 Q10（麦麦外接 ACP Planner）、§3.2 Q3（Letta："限制放在使用处"）；papers-architecture §2.4（AIOS 系统调用）、§4 |
| P4 | 一个中心，多路并行 | 只有主意识做全局决定；会话之间不直连，向上发通知，向下收广播 | 决策 11–13；papers-architecture §2.2、§3.5 修正 A、§6 D；companion-architectures §9 坑 1 |
| P5 | 代码先判断，模型后到场 | 起不起回合、唤不唤醒、要不要升级，先由代码判定；模型只在必要时运行，可以安静返回 | papers-architecture §5、§7.1；companion-architectures §8 共识 2；openclaw-architecture §2.2 Q5 |

### 1.3 非目标

明确不做的事，用来挡住"顺手加上"的复杂度：

- **多主人、多租户。** 一个本体就是一个主人的信任边界（依据：product.md「灵鲸里有谁」；openclaw-architecture §2.2 Q8）。Letta 把通用多租户服务端整个退役，说明这条路维护很重（依据：companion-architectures §9 坑 11）。
- **多主机、云托管、中继。** 只跑在主人自己的机器上，远程访问走 Tailscale（依据：product.md「不做什么」；paseo-architecture §3 最后几行）。
- **公开的插件或技能市场。** OpenClaw 的技能市场被大规模投毒（依据：openclaw-architecture §2.2 Q10 用户痛点第 2 条、§5 坑 12）。
- **旧协议兼容。** 前端由本体托管、同版本发布，不维护兼容矩阵（依据：client-backend §2、§3.3）。
- **通用 agent 平台。** 系统里没有无人设的普通 agent（依据：决策 5）。

## 2. 核心概念与数据模型

### 2.1 概念表

| 概念 | 是什么 | 关键属性 | 版本 |
| --- | --- | --- | --- |
| 主人 | 唯一的主人，"真人"的特例 | 主人绑定的各平台账号；本机主控台登录 | V1 |
| 数字生命（成员） | 她，以后还有朋友；一个完整的人格边界 | 出生设定、成长、当下状态、作息、记忆、关系、技能、自主开关、大脑配置 | V1 只有她；V3 多成员 |
| 她的状态 | 某个成员此刻"是谁、记得什么、答应了什么、定过什么方针"的总和 | 全部是日志投影，分属各灵魂模块管理；整体带一个版本号 | V1 |
| 主意识 | 成员唯一能看全局、做全局决定的位置；运行时表现为一个常驻的主意识会话 | 只有主人和她自己能进；自主开关关闭的成员没有主意识 | V1 |
| 会话 | 一个 CLI 会话在本体这边的"外壳"：谁在执行（哪个成员的人设）、在什么位置、绑哪个大脑 | 种类、所属成员、绑定对象（场合、任务或作业）、父会话、大脑、CLI 句柄（只是缓存）、会话令牌、状态 | V1 |
| 在场分身 | 守一个非主人场合的会话 | 每个场合一个；只拿受众都能知道的记忆；不做全局决定 | V2 |
| 干活分身 | 守一件活的会话 | 每件活一个；可开子会话 | V1 |
| 内省会话〔新提议 N1〕 | 后台整理记忆、写日记、提成长的隐藏会话，执行者是她自己 | 不对外说话；只交结构化产出；用完即弃 | V1 |
| 朋友 | 另一个数字生命 | 自己的人设和记忆；被叫来时以会话出现 | V3 |
| 真人 | 关系网里的人，不是会话 | 身份声明、主人设定的关系、她对此人的印象 | V2（V1 只有主人） |
| 身份声明 | "某平台的某个账号属于某个真人" | 验证级只有两档：观察到、主人绑定 | V2 |
| 成员账号 | 成员自己在某平台的账号，例如她的 QQ 号 | 路由键里带账号 | V2；V5 多成员各用自己的账号 |
| 场合 | 对话发生的地方 | 种类（主人·主控台、主人·某平台私聊、某人私聊、外部群、内部群、成员之间私聊）；成员快照；受众 | V1 只有"主人·主控台" |
| 受众 | 一个场合里所有在场者都有资格知道的范围 | 取所有在场者的最小权限；成员快照过期或不确定时按最严处理 | V2 起真正生效 |
| 操作日志事件 | 唯一事实来源里的一条记录 | 流、流内序号、类型、执行者、因果链、来源信息（场合、受众、来源人、可信度） | V1 |
| 通知 | 进主意识收件箱的简短事件 | 类别、紧急度、一两句话、报告引用、相关对象 | V1 |
| 关注清单 | 主意识登记的"这类事有消息就优先告诉我" | 匹配条件、效果、能否突破、到期时间 | V1 |
| 方针（近期决定） | 主意识做出的全局决定，例如"这周别在群里提主人的事" | 适用范围、受众、到期、理由 | V1 |
| 状态表 | 给主意识看的一张短表 | 手上的活、待决请求、临近的承诺、关注项；每行带更新时间和来源 | V1 |
| 任务 | 一件活 | 状态机、交接包、工作区、审核点 | V1 |
| 承诺 | 她答应的事 | 原话、对谁、何时、绑定的作业 | V1 |
| 日程 | 她的时间安排 | 承诺、作息、主人日历【V4】的合成视图 | V1（主人日历 V4） |
| 作业 | 统一的定时或事件触发单元 | 触发条件、目标、策略 | V1 |
| 记忆条目 | 记忆投影里的一条 | 种类（情景、事实、关系；领域【V3】）、内容、来源、受众、证据事件 | V1 |
| 成长版本 | 人格枝叶的一个版本 | 提案、证据、生效、回滚 | V1 |
| 技能 | 学会的本事和自己做的工具 | 版本、隔离 | V4 |
| 快照、回收站条目 | 可撤销兜底的对象 | 属于哪件活、哪个会话 | V1 |

**为什么多出"内省会话"这一种。** 决策 4 规定后台任务（记忆抽取、每晚整理、写日记）也调 CLI，决策 5 规定系统里没有无人设的普通 agent。两条合起来，后台任务的执行者只能是她自己：日记要用她的口吻写，成长提案是她对自己的反思。它和三种会话都不一样：不对外、不面对任何人、只交结构化产出，所以单列一种。AIRI 的后台任务就是"同一人设的隐藏会话"，是四个陪伴类项目里唯一让后台任务"是她"的做法（依据：决策 4、5；companion-architectures §4.2 Q1、§8 对比表"子 agent 的人设"一行；paseo-architecture §3"agent-response-loop"一行）。它和决策 12 的"三种会话"是否冲突，见 §17.1 N1。

三条关系需要说清楚：

1. **场合和会话是两样东西。** 场合是外界的地址，会话是她在那里的在场。好处是：会话换新、换大脑都不改场合；主人在多个形态上的私聊可以是多个场合，却汇进同一个主意识会话。OpenClaw 也把 session 和外部地址 `conversationRef` 分开，多个私聊地址可以共用一个 main 会话；eliza 的 Room 也是独立对象（依据：openclaw-architecture §7 B；companion-architectures §5.2 Q2；决策 11）。
2. **主人的主控台和网页是同一个场合。** 两者是同一个主人在同一个界面上，回复应该同时出现在所有打开的客户端上。麦麦的网页聊天室和桌宠也共用一个 `owner` 聊天流（依据：companion-architectures §2.2 Q3）。主人的 QQ 私聊【V2】是另一个场合，同样进主意识。
3. **真人不是会话。** 真人是关系网里的人，存在本体里；她和某个真人说话，发生在某个场合里，由那个场合的会话负责（依据：决策 12）。

自主开关关闭的成员【V3】没有常驻主意识。主人在主控台直接找它时，本体按需开一个它自己的会话：结构和主意识会话一样，但没有自主触发、关注清单和作业，闲置就回收〔新提议 N2〕。依据是 product.md「谁能叫醒开关关闭的伙伴」（主人可以在主控台直接找伙伴对话）和决策 12（关着的朋友只在被叫来时以会话出现），但这个会话的形态是本稿推出来的。

## 3. 系统分层与进程模型

### 3.1 进程模型

```
launchd（KeepAlive：进程退出就拉起）
└── 本体：一个 Node 24 进程
      ├── 主线程：事件循环 + 唯一的 SQLite 写入者
      ├── worker_threads：只读的重查询（日志全文检索、投影重建），各开只读连接
      ├── CLI 子进程 ×N：每个活着的会话一个
      │     claude（经 Claude Agent SDK 拉起）｜ codex app-server（stdio）｜ 通用 ACP CLI（stdio）
      │     └── 用户给 CLI 配的第三方 MCP 服务：由 CLI 自己拉起，不经本体
      ├── 形态适配器子进程 ×N【V2 起】：QQ、微信、B 站……每个一个进程〔新提议 N3〕
      └── 本地能力服务【按需】：SenseVoice 等原生模型的子进程；Python 模型服务〔新提议 N3〕

数据目录：liwa.db（日志 + 内联投影）· derived.db（异步投影，可重建）〔新提议 N6〕
          · blobs/ · members/<id>/cli-home/ · workspaces/ · trash/ · backups/
客户端：浏览器经 HTTPS / WebSocket 连本体（默认只听本机回环；远程经 Tailscale Serve）
```

术语：

- **进程**：操作系统里独立运行的程序，一个进程崩了不会带崩别的进程。**子进程**：由本体启动、由本体负责回收的进程。
- **事件循环**：Node 用一个线程依次处理所有请求，这个循环被同步的重活堵住时，整个本体都会卡住。
- **worker_threads**：Node 的后台线程，用来跑重活而不堵事件循环。
- **MCP**：让 CLI 调用外部工具的标准协议；本体的"内核工具"就是经它（或 CLI 支持时经原生工具注入）提供给 CLI 的。

**为什么是"一个进程 + 子进程"。**

- 单主人、单机，模块化单体足够。OpenClaw 是一个 Gateway 进程，Letta Code 是一个 Node 进程，Paseo 的所有子系统也在同一个 worker 进程里（依据：openclaw-architecture §2.2 Q1；companion-architectures §6 A；paseo-architecture §2.2 Q1；client-backend §3.1）。
- 放弃 Paseo 的 supervisor + worker 两级进程：拉起崩溃进程的事交给 launchd 就够了（依据：paseo-architecture §3"两级进程"一行；client-backend §3.1）。
- 放弃把认知放进界面进程：AIRI 的 agent 跑在渲染进程里，要靠多窗口选主，想做无界面常驻至今没做成（依据：companion-architectures §9 坑 13）。
- 放弃拆成多个服务：单人维护成本高，跨服务还要处理一致性；Letta 的多租户服务端已经整个退役（依据：companion-architectures §9 坑 11）。
- 写只在主线程、只有一个写入者；重查询放 worker_threads。node:sqlite 的接口全是同步的，上游 Paseo 近几个版本一直在修"堵事件循环"（依据：client-backend §2、§3.1；openclaw-architecture §2.2 Q1 WorkerTaskPool）。

### 3.2 分层与依赖方向

```
接入层   gateway（客户端）           toolport（内核工具端点，给 CLI 会话用）
编排层   gate    mind    tasks    scheduler    outbox
运行层   conversations    context    actions
灵魂层   roster    persona    memory    social    agenda    skills【V4】
资源层   brains    procs    formhost    abilities    workspace    notify
守护     guard（运行层和 abilities 在每个回合、每个动作之前调用它）
基础层   journal（操作日志、投影运行器、大对象存储）
```

每层是什么：

- **接入层**：外界怎么跟本体说话。主人的客户端和 CLI 会话对本体来说都是"外面"。
- **编排层**：认知循环里由代码做的判断：消息去哪、什么时候起回合、谁的活、对外说给谁。
- **运行层**：把回合跑起来、把动作执行掉。
- **灵魂层**：她的状态，每个模块管一块。
- **资源层**：本体用到的外部资源：CLI、进程、外部平台、模型服务、文件、主人的设备。
- **守护**：横切所有动作的闸。
- **基础层**：日志。

四条依赖规则（依据：client-backend §3.1"依赖单向，各自拥有自己的表"；paseo-architecture §2.2 Q1"依赖单向，但几个类太大"、§5 坑 12；companion-architectures §3.2 Q7"Letta 的分层由 CI 强制，源文件不超过 1000 行"）：

1. 调用只能向下。同层之间只能调公开 API，而且不能成环。
2. 向上传信息只有两条路：持久的事走日志事件订阅，例如 tasks 写下"设计已提交"，mind 订阅后生成通知，tasks 不需要认识 mind；不需要持久的走进程内信号，例如客户端在线状态。
3. 每个模块只读写自己的表；别的模块的数据只能经它的查询 API 或它发出的事件拿到。
4. 依赖方向和单文件行数上限由检查工具强制，不靠自觉。

### 3.4 CLI 子进程的监管与回收

| 步骤 | 做法 | 依据 |
| --- | --- | --- |
| 拉起前 | guard 准入（暂停、总闸、全局并发上限）；procs 先把身份登记进 SQLite（父进程、所属会话、命令行指纹的摘要），再拉起，再握手 | openclaw-architecture §2.2 Q1"Codex 怎么回收" |
| 拉起时 | 放进单独的进程组（一组可以一起杀掉的进程，CLI 派生的子孙进程都在里面）；每个成员一个 CLI 数据目录（如 Codex 的 `CODEX_HOME`），放在本体的数据目录下 | openclaw-architecture §2.2 Q1 `homeScope`；client-backend §4 坑 7 |
| 握手 | 有时限；Codex app-server 没有版本协商，只按大版本判断兼容 | openclaw-architecture §2.2 Q1、§5 坑 10 |
| 运行中 | 适配器必须把"CLI 在两个回合之间死掉"也报成回合失败；回合看门狗：一段时间没有任何事件就中断 | paseo-architecture §2.2 Q5"CLI 崩溃"、§5 坑 7、坑 9；openclaw-architecture §2.2 Q5（60 分钟看门狗） |
| 中断 | 幂等；中断被拒或超时就"失败即关闭"：不再给这个会话派新回合，避免两个回合同时写 | paseo-architecture §2.2 Q4"中断与 steer 的规则" |
| 闲置回收 | 空闲超过阈值，且适配器的 `canStopRuntime()` 不否决（后台 shell、终端还在跑就否决）→ 关进程，保留记录，下次有输入再续接 | paseo-architecture §2.2 Q9（0.14 空闲回收） |
| 孤儿清理 | 本体启动时、每次拉起新进程前，只清"已登记、原父进程已不在、指纹对得上"的进程；查不清或清不掉就拒绝再拉起，并通知主人。**孤儿进程**指父进程死了以后还在跑、没人管的子进程 | openclaw-architecture §2.2 Q1；paseo-architecture §3"managed-processes"一行 |
| 续接失败 | 用同一个大脑开新会话，上下文从日志重建，不读旧 CLI 的转录 | paseo-architecture §3"交互式 agent 不切换备用大脑"一行；本稿 §6.4 |

### 3.5 插件和外部依赖放进程内还是进程外

OpenClaw 的教训是：单进程里一个外部依赖就能拖垮全局。一个 stdio MCP 服务 30 秒没完成握手，清理路径抛出未处理的异常，整个 Gateway 退出，所有渠道一起掉线（#144911）；工具子进程不回收，僵尸进程越积越多（#97616）；网关内存两三天涨到 15.5 GB（#91588）（依据：openclaw-architecture §8.1.2"进程崩溃和恢复"、§8.1.3 第 5 条）。放进程外的代价是多一层 IPC（进程之间传消息的通道）的序列化和生命周期管理；好处是崩溃、内存泄漏都关在那一个进程里。取舍规则：**一方写的核心路径放进程内；依赖第三方协议栈或原生代码的放进程外。**

| 组件 | 放哪 | 理由 | 依据 |
| --- | --- | --- | --- |
| 大脑适配器的代码 | 进程内（CLI 本身是子进程） | 一方代码，要低延迟拿事件；CLI 崩溃天然隔离在子进程里 | paseo-architecture §2.2 Q1、Q7 |
| 第三方 MCP 服务 | 由 CLI 自己拉起，不经本体 | 失败只影响那一个会话，正好避开 #144911 | paseo-architecture §2.2 Q7"用户 MCP 由 CLI 自己连接"；openclaw-architecture §8.1.1（#144911） |
| 内核工具端点 | 进程内 | 它就是本体的行动入口 | paseo-architecture §2.2 Q7 |
| 主控台、网页接入 | 进程内（gateway） | 一方代码，核心路径 | client-backend §3.1 |
| 外部平台的形态适配器 | 每个一个子进程〔新提议 N3〕 | 依赖 NapCat 这类第三方协议栈，长连接、内存泄漏、崩溃风险都高；崩了只让那一个形态离线 | companion-architectures §2.2 Q7（麦麦插件 Runner 子进程 + 健康检查 + 最大重启次数 + 熔断）；paseo-architecture §2.2 Q7（插件 server 端在子进程）；companion-architectures §4.2 Q7（AIRI 集成是独立进程） |
| 线上能力实现 | 进程内 | 只是 HTTP 调用，超时和取消信号就能管住 | ability-plugins §3.1 |
| 本地能力模型 | 子进程或 Python 服务〔新提议 N3〕 | sherpa-onnx-node 这类原生扩展一旦段错误会带崩本体；重模型吃内存 | 决策 3；ability-plugins §3.5"重型模型用 Helm 式独立工作进程隔离" |
| 重查询 | worker_threads | 不堵事件循环 | client-backend §3.1 |
| 技能与自写工具【V4】 | 单独的隔离通道 | 不可信代码，不能走"完全信任"的插件通道 | openclaw-architecture §5 坑 12；paseo-architecture §5 坑 13 |

为了让同一个形态适配器既能在子进程里跑、也能在测试时直接加载，适配器开发包定义成一套**消息协议**，不定义成进程内的函数接口；子进程由 formhost 托管：健康检查、重启次数上限、熔断（连续失败后暂时不再重试）（依据：companion-architectures §2.2 Q7 maim_message；openclaw-architecture §2.2 Q7 插件只能走公开 SDK 入口）。

### 3.6 并发

**不同会话之间默认全部并行。** 主意识、每个在场分身、每个干活分身各自独立运行，互相不等；不按会话种类分别设配额，只有正在跑的会话总数达到并发上限时才排队（见下）（依据：决策 12，三种会话各自独立；用户 2026-10-28 明确在场分身和干活分身应该并发）。

另有两处是"一个一个来"，它们和并发上限无关：

| 规则 | 为什么 | 依据 |
| --- | --- | --- |
| 同一个会话同一时刻只跑一个回合；新消息合进当前回合或下一轮（§4.7） | 一个会话就是一段对话，同时跑两个回合会互相覆盖、重复回复 | openclaw-architecture §2.2 Q2（会话控制器邮箱）；paseo-architecture §2.2 Q2（同一时刻最多一个前台 turn） |
| 内省会话同一时刻只跑一个，主人正在用时让路 | 它们改的是同一份记忆和成长，并行会写冲突；它们不赶时间 | companion-architectures §7.4（Letta 反思子 agent 同一 agent 同时只跑一个） |

**并发上限：一个可配置的数量，达到就排队。** 主人在主控台设一个数字：同一时刻最多有几个会话在跑回合（用户 2026-10-28 定）。没达到上限时全部并行；达到上限后，新回合按到达先后排队，前面有回合结束就放行下一个，消息不丢，主控台显示正在排队的会话。

- 主意识不排队：它在上限里有一个预留名额，主人的消息永远不会排在后台回合后面。
- 只算"正在跑回合"的会话：闲置会话的进程会被回收（§3.4），不占名额，所以平时排队很少见。
- 默认值按实测定（§16 第 21 条：每个 CLI 进程跑回合时占多少内存、各模型服务商允许多少并发请求）。
- 子会话的派生深度另有上限，防止无限派生。

依据：openclaw-architecture §2.2 Q2（全局 lane 有并发上限，超出排队）、§2.2 Q3（子 agent 深度默认 5）；papers-architecture §6 A（AIOS 的全局并发上限和队列）；paseo-architecture §6（没有全局上限，是反例）；openclaw-architecture §8.1.2 #91588（网关内存两三天涨到 15.5 GB）；early-findings §4（mac mini 是 M4、24 GB）。"模型服务商有并发限制"是推理，要实测确认。

### 3.7 客户端怎么连

本体同时托管 React 前端和 WebSocket 接口，前后端同版本发布。默认只听本机回环地址；远程访问经 Tailscale Serve 提供 HTTPS，并要求令牌。Electron 以后作为薄壳直接加载本体地址（是否第一版就做，见 §17.3 P3）。协议和同步细节见 §10，鉴权见 §11（依据：client-backend §3.3、§3.7；paseo-architecture §2.2 Q8）。

## 4. 认知循环与事件流

### 4.1 一个回合的六段

循环由本体的代码驱动，不由任何 CLI 会话驱动。CoALA 把决策过程定义为"agent 代码里的 main 程序"；CLI 里的工具循环只是第四段"决策"内部的事（依据：papers-architecture §2.1 CoALA §4.6、§6 A）。下表的"一个回合"指主意识或任何一个会话的一次决策；在场分身、干活分身跑的是同构的小循环（依据：papers-architecture §4）。

| 段 | 做什么 | 谁做 | 关键规则 | 依据 |
| --- | --- | --- | --- | --- |
| ① 感知 | 外界事件归一成入站事件（平台、成员账号、场合地址、发送者、内容段、@ 列表、回复对象、平台消息号）；按平台消息号去重；认人、算场合和受众；**先写日志**；语音和图片经能力插件转成文字，作为派生事件挂在原事件上；回流的自己的消息标成"她说的" | formhost / gateway、social、journal、abilities | 先落日志再做别的；来源信息第一版就写全 | openclaw-architecture §2.2 Q7；companion-architectures §2.2 Q7（麦麦 platform_io 去重和路由键）、§9 坑 4；client-backend §3.2；决策 7 |
| ② 门控 | 用代码决定去向：主人私聊进主意识；别人私聊进对应在场分身；群消息过两道门；斜杠命令直接处理 | gate | 不调大模型；不过门就不起回合 | 决策 13⑥；companion-architectures §2.2 Q1、§3.2 Q3 |
| ③ 进入主意识 | 内部事件按规则变成通知，进收件箱；合并、去重、排序、配额；主人的消息走突破通道 | mind | 进不进由外围规则加主意识的关注清单决定，不由主意识自己挑 | 决策 13①；papers-architecture §3.3 13-2、§3.5 修正 A；paseo-architecture §2.2 Q9 |
| ④ 决策 | 邮箱放行一个回合 → guard 准入 → 组装注入层 → 交给 CLI；CLI 在回合内自己跑工具循环，要对外做事就调内核工具 | conversations、guard、context、brains | 每回合有工具调用次数和步数上限 | openclaw-architecture §2.2 Q2；paseo-architecture §2.2 Q3；决策 13④；papers-architecture §3.4 |
| ⑤ 行动 | 内核工具调用 → 令牌认出是哪个会话 → 工具是否在它的工具集里 → 交给所属模块 → 行动管线：准入、目标与受众检查、记"将要做"、执行、记结果 → 结果同步返回给 CLI〔新提议 N4〕。干活分身的 CLI 原生工具经权限钩子：worktree 内按白名单放行并先打快照，其余交主人 | toolport、outbox / tasks / agenda / memory、actions、workspace | 会话只提出动作；本体执行 | companion-architectures §7.1（麦麦"MCP 只收决策"）、§5.2 Q8（eliza"先持久化派发再执行"）；paseo-architecture §2.2 Q8 |
| ⑥ 写回与学习 | 回合结束带用量 → guard 记账 → 内联投影（时间线、看板、状态表、花费）更新 → 通知标记已消费 → 有全局决定就让她的状态版本加一，相关会话下一轮收到提醒 → 稍后由内省作业批量抽记忆、做整理 | conversations、guard、journal、agenda、scheduler | 学习异步、按批、按空闲；不在回复路径上做 | papers-architecture §4 ⑤⑥、§5.3；决策 13②⑤；paseo-architecture §3（用量改为必填） |

**〔新提议 N4〕内核工具在调用当中同步执行。** 麦麦的外接 ACP Planner 让 MCP 只记录"决策"、回执"已受理未执行"，等外部回合结束再由麦麦执行（依据：companion-architectures §2.2 Q10）。灵鲸保留它的要点：执行权、准入和写日志都在本体；但改成在工具调用当中同步执行完再把结果返回 CLI。理由有两条：一是 CLI 往往要用结果接着做，例如派活后要拿到任务号、回复后要知道是否送达；二是"模型拿到'已受理未执行'之后会不会正确结束回合"在 Claude Code 和 Codex 上还没验证过（依据：companion-architectures §10 第 3 条）。耗时长的动作（例如生成一段语音）先返回"已受理"和编号，做完以事件回报。

### 4.2 每个会话注入什么

注入分两个时机：**会话创建时**一次性放进去的，和**每一轮**放在本轮输入前面的。稳定内容放在模型服务商"前缀缓存"能命中的位置；**前缀缓存**指服务商对和上次完全相同的开头部分打折计费，开头一变就要按全价重算。所以易变内容一律放在后面，系统提示里也不放消息号、时间戳这类每轮都变的东西（依据：openclaw-architecture §2.2 Q4、§8.1.2 #20894 和 #143017；决策 13④）。

| 层 | 何时 | 放在哪 | 上限 | 来源 | 依据 |
| --- | --- | --- | --- | --- | --- |
| 人设：出生设定 + 当前成长版本 | 会话创建 | CLI 原生指令字段**追加**（Claude preset + append、Codex `developer_instructions`；ACP 退到工作目录指令文件或提示词前缀）；缓存边界上方 | 合计约 6 万字符、单块约 2 万；超了截断并加固定提示 | persona | 决策 4；openclaw-architecture §2.2 Q4；companion-architectures §7.5 |
| 会话角色说明：这种会话的规矩、工具用法 | 会话创建 | 同上 | — | conversations | openclaw-architecture §2.2 Q4（AGENTS.md 的作用） |
| 绑定对象的说明：交接包（干活）、场合说明（在场）、作业说明（内省） | 会话创建 | 首条消息 | — | tasks、social、scheduler | 决策 14 |
| 最近对话：从日志取最后 N 轮原文 | 会话创建（含换新、换大脑） | 首条消息 | N 轮 | journal | papers-architecture §3.3 13-5 |
| 当下状态 | 每轮，变了才带 | 本轮前缀，缓存边界下方 | 一两句 | persona | 决策 13④；ability-plugins §3.2 |
| 广播提醒：方针、承诺的变化 | 每轮，有变化才带 | 本轮前缀 | 条数上限 | agenda | 决策 13② |
| 状态表（只给主意识） | 每轮，变了才带 | 本轮前缀 | 行数上限 | mind | 决策 13③ |
| 预取摘要：输入里提到的活、人、场合 | 每轮，命中才带 | 本轮前缀 | 条数上限 | mind 匹配，tasks / social 给摘要 | 决策 13③；papers-architecture §3.5 修正 D |
| 召回记忆 | 每轮 | 本轮前缀 | 条数、字数上限 | memory，按本会话受众过滤 | 决策 13④ |
| 收件箱通知（只给主意识） | 每轮 | 本轮前缀 | 配额 K 条 | mind | 决策 13① |
| 本轮输入：主人的话、场合消息 | 每轮 | 正文，信封包装，人发的伪信封会被转义 | — | gate | paseo-architecture §2.2 Q9（agent-messages 信封） |

主意识是常驻会话，CLI 自己记得这个会话里说过的话，所以"最近对话"只在新开会话时从日志补，不每轮重复注入。

### 4.3 链路一：主人私聊

```
主人（主控台或网页）
 ① 发消息：WebSocket 请求，带幂等键
 ▼
gateway：归一成入站事件，场合 = 主人·主控台
 ▼
journal ② 追加 message.received{来源人: 主人, 场合: 主人·主控台, 受众: 主人}
 ▼
gate ③ 发送者是主人 → 主意识（突破通道）
 ▼
conversations（主意识的邮箱）④
   ├ 主意识空闲：收 0.5–2 秒内的连发，合成一轮
   ├ 正在跑主人发起的回合：在工具批次之间 steer 进去
   └ 正在跑通知或自主触发的回合：在安全点抢占〔新提议 N5〕
 ▼
guard ⑤ 准入：没有暂停、总闸没拉（主意识在全局并发上限里有预留名额）
 ▼
mind + context ⑥ 组装本轮前缀：
   当下状态（变了才带）· 方针与承诺的变化 · 状态表的变化
   · 预取：主人提到"那个网站的活" → 按实体匹配注入该任务的最新进度摘要
   · 召回记忆 · 收件箱里排上号的通知 · 主人原话（信封包装）
 ▼
brains ⑦ startTurn → Claude Code 子进程（DeepSeek V4.1 Flash）
 ▼  模型调用内核工具 reply(事件号 = ②, 内容)；不调用就等于没回（兜底见 §8 R10）
toolport → outbox → actions ⑧
   令牌 → 这是她的主意识会话，reply 在它的工具集里
   目标 = ② 所在的场合（由事件带来，不看会话记着什么）
   记 effect.intended → 写 message.sent → gateway 推给所有打开的主控台和网页 → 记 effect.completed
 ▼
⑨ turn.completed{用量} → guard 记账 → 时间线、状态表投影更新 → 用到的通知标记已消费
⑩ 稍后：内省作业按批从日志里抽事实记忆和关系记忆
```

要点：

- **跨形态连续。** 主人第二版从 QQ 私聊发来的消息进的是同一个主意识会话，回复的目标是那条 QQ 消息所在的场合（依据：决策 11；product.md「形态」"跨形态连续"）。
- **主人体验 = 主意识大脑的质量。** 所有主人私聊都进主意识，主意识大脑选得不好，主人第一个感受到（依据：papers-architecture §3.1 11-4）。缓解办法见 §17.2 C1。
- 回复是工具调用，主控台上的"逐字吐出"取决于适配器能不能流式拿到工具参数，列入待实测；拿不到就先显示"正在输入"，整条到了再显示（§16 第 4 条）。

### 4.4 链路二：群聊消息【V2】

```
群友在 QQ 群 G 里说话
 ▼
QQ 形态适配器（子进程）① 归一：平台消息号、发送者账号、@ 列表、回复对象、内容段
 ▼
formhost → social：认人（只认身份声明）、算场合键、取成员快照 → 受众
 ▼
journal ② 追加 message.received{场合: G, 受众: G 的成员快照, 来源人: 某群友或陌生人}
   没唤醒她的消息也记下：它们是 G 的历史，下次唤醒时作为上下文
 ▼
gate ③ 第一道门（代码）：@ 她、叫她名字、回复她、主人在说话 → 唤醒
       第二道门（不调大模型）：话题和她的兴趣、近期记忆做向量相似度，过阈值才唤醒
       两道都没过 → 到此为止，不起回合
       防抖：安静 2 秒 / 活跃 5 秒 / 整批最多 8 秒 / 被 @ 后最多 1 秒
 ▼
conversations：G 的在场分身（没有就创建：注入她的人设 + 只限 G 受众的记忆快照）
 ▼
guard ④ 准入：暂停、总闸、全局并发上限
 ▼
context ⑤ 本轮前缀：广播提醒（只含 G 的受众能知道的方针和承诺变化）· 受众内召回 · 新消息
 ▼
brains ⑥ 回合
 ├ 情况 A：她决定接话 → reply(事件号, 内容)
 │     outbox：目标只能是 G；出站清洗 → formhost 投递 → 平台回执写日志
 ├ 情况 B：不接话 → 什么都不调用，回合安静结束
 └ 情况 C：涉及全局（有人约她周六出去、问到主人的事、主人 @ 她派活）
       request_global_decision(类别, 问题, 原消息号) 或 forward_to_main(原消息号)
       → 她在群里先用自己的口吻稳住（"我问问""等我想想"），不替主意识做决定
       → mind 生成通知进收件箱 → 主意识回合：commit / decide / dispatch
       → agenda 版本加一 → G 的在场分身下一轮开头收到提醒 → 她在群里给出答复
```

要点：

- 两道门的结构来自决策 13⑥；防抖参数取麦麦的默认档，权重和阈值要用灵鲸自己的数据重拟，第二版先用规则（依据：companion-architectures §2.2 Q1、§7.3、§10；papers-architecture §3.5 修正 H）。
- 第二道门只管"要不要叫醒"，叫醒以后"说不说"由模型判断，可以安静结束。原因是在谁都能接话的场合，表面特征几乎预测不了该不该开口（依据：papers-architecture §2.7 Inner Thoughts §3）。
- 群友说"周六一起玩"，群分身答应了，私聊分身又说"周六要陪主人"：这类冲突发生在共享状态上。所以许诺只能由主意识经 agenda 写入，在场分身只能提请（依据：决策 12；papers-architecture §3.2 12-4）。
- 她自己发出去的消息从平台回流时标成"她说的"，防止自己回复自己（依据：companion-architectures §9 坑 4，麦麦 #1854）。

### 4.5 链路三：自主触发（以早安为例）

```
scheduler ① 作业"早安"到点
   时间来自作息；策略：只在活跃时段、只在主意识空闲时、每日上限 1
 ▼
② 第一道闸 shouldRun（不加载上下文，很便宜）：
   自主开关开着？没暂停？在活跃时段？主人今天日历显示很忙【V4】？最近几次主动没被理睬 → 退避？
   没过 → 记 job.skipped，结束
 ▼
journal ③ 追加 job.fired → mind 订阅后生成通知{类别: 自主触发, 紧急度: later}
 ▼
mind ④ 等主意识空闲；把夜里内省会话备好的材料挂成报告引用：
   今天到期的承诺 · 昨晚干活分身的结果 · 今天的日程
 ▼
guard ⑤ 准入
 ▼
⑥ 第二道闸 canExecute（带完整上下文）：材料为空、也没有值得说的 → 不起回合，结束
 ▼
brains ⑦ 主意识回合：模型判断说不说
 ├ 说：sayToOwner(内容) → outbox 按主人的在线情况选场合
 │      （主控台在线就发主控台；不在线时用主人设定的首选形态【V2】）→ 投递 → notify 弹通知
 └ 不说：回合安静结束，记 turn.completed{安静}
 ▼
⑧ 主人之后的反应（回复、点开、忽略、"别烦我"）写进日志，作为调整频率和阈值的依据
```

要点：

- 早安、提醒、闲时整理全部是同一种作业，按属性区分，不另设心跳（依据：openclaw-architecture §8.2；详见 §7.1）。
- 两道闸分开，是为了不为了"跳过"而去加载整个上下文（依据：companion-architectures §5.2 Q4，eliza v2 的 `shouldRun` 和 `canExecute`）。
- 触发由代码判定，模型只在触发之后判断说不说（依据：companion-architectures §4.2 Q4，AIRI"Code decides each trigger … without a model call"；papers-architecture §5.2）。
- 夜间整理的产出对准第二天能预测的需要，所以早安的材料是现成的，回合可以很短（依据：决策 13⑤；papers-architecture §2.4 sleep-time compute）。

### 4.6 链路四：干活分身完成任务

```
干活分身（Codex 子进程，在任务 T 的 worktree 里）
 ① 做完，调用 report(T, 阶段: 待验收, 摘要, 产物: 改动文件、测试结果)
 ▼
toolport → tasks ② 完成核验（代码）：
   声称改了的文件真的有 diff？声称跑过的测试有执行记录并通过？声称的产物都在？
   核验不过 → 退回分身（"以下说法和实际对不上：…"），不进入待验收
 ▼
actions ③ 先写日志：task.stage_changed{执行中 → 待验收, 核验结果}
 ▼
④ 两条线同时走，都从这条日志事件出发，至少送达一次：
   ├ notify：这是要主人审核的事 → 直接按主人在线情况推送（不等主意识决定）
   └ mind：生成通知{类别: 活的里程碑, 一两句话, 报告引用: T 的进度摘要}
           → 收件箱（持久化；主意识回合成功结束才标记已消费，失败就重新投递）
 ▼
⑤ 主意识下一轮看到通知：sayToOwner("网站那个活做完了，等你验收")；也可以只更新状态表、不说话
 ▼
⑥ 主人在主控台打开 T：看 diff → 验收；或者打回，打回意见作为主人直连消息进分身
 ▼
tasks ⑦ 待验收 → 完成；workspace 把 worktree 合回主线（冲突在这一步暴露给主人）
 ▼
⑧ 内省作业把这件活抽成她的情景记忆："这件活是我做的"（来源：分身）
```

要点：

- 子任务结果会静默丢失、"文件已创建"可能是假的，OpenClaw #44925 在生产环境至少出现 9 次。所以汇报先落日志再投递、失败重投，可以核对的说法在进入待验收前由代码核对（依据：openclaw-architecture §8.1.1、§8.1.3 第 3 条）。MAST 的实验里，加一步"对照总目标核验"成功率提高 15.6%（依据：papers-architecture §2.5 MAST）。
- "至少送达一次"照 Paseo 上游 0.13 的完成订阅：先写订阅意图，再承诺投递，重启后恢复观察（依据：paseo-architecture §2.2 Q9）。
- 需要主人审核的事直接推给主人，不交给主意识决定要不要说：主意识只负责提醒，不能挡在主人和审核之间（依据：paseo-architecture §3"子 agent 的权限请求"一行；client-backend §3.6）。
- 一件活一个 worktree，合回主线放在主人验收之后，这就是"同一工作区的文件单点写"的落实（依据：决策 12；client-backend §2"多任务控制台"并行靠 worktree）。**worktree** 是 git 的功能：同一个仓库可以同时检出多份互不干扰的工作目录。

### 4.7 会话邮箱：同一会话内的消息怎么处理

每个会话有一个邮箱，同一时刻只放行一个回合（依据：openclaw-architecture §2.2 Q2"会话控制器邮箱"；paseo-architecture §2.2 Q2"同一时刻最多一个前台 turn"）。两个动词：**steer** 是把新消息塞进正在跑的回合（在一批工具调用结束、模型做下一次决定之前）；**interrupt** 是中止当前回合。

| 会话 | 来的东西 | 会话空闲时 | 会话正忙时 | 依据 |
| --- | --- | --- | --- | --- |
| 主意识 | 主人的消息 | 收 0.5–2 秒内的连发，合成一轮 | 正跑主人发起的回合 → steer；正跑通知或自主触发的回合 → 抢占〔新提议 N5〕 | openclaw-architecture §2.2 Q2（collect、steer、500 ms 防抖）；paseo-architecture §3"按接收方排队"一行 |
| 主意识 | 通知 | 2 秒安静窗口合并后开一轮 | 等当前回合结束；可突破的类别在工具批次之间 steer 进去 | paseo-architecture §2.2 Q9；决策 13① |
| 主意识 | 自主触发 | 开一轮 | 等空闲，不算失败 | openclaw-architecture §2.2 Q5 `idleOnly`；paseo-architecture §5 坑 4（撞上正忙就算失败是反例） |
| 干活分身 | 主人直连的补充要求 | 开一轮 | steer | openclaw-architecture §3"会话控制器邮箱"一行；paseo-architecture §3"人发消息默认 interrupt"一行 |
| 干活分身 | 主人"叫停" | — | interrupt（幂等，失败即关闭） | paseo-architecture §2.2 Q4 |
| 干活分身 | 子会话结果 | 开一轮 | steer | paseo-architecture §2.2 Q9（0.12 起 agent 间消息改为 steer） |
| 在场分身 | 场合消息 | 防抖后开一轮 | 等当前回合结束再合批 | companion-architectures §2.2 Q1 |
| 任何会话 | 广播提醒 | 下一轮开头 | 下一轮开头，不打断 | 决策 13② |
| 任何会话 | 斜杠命令（/暂停、/叫停） | 本体直接处理，不进模型 | 同左 | companion-architectures §3.2 Q3 |

另外三条规则：

- **只有发起者能 steer 自己发起的回合。** 别人的消息不 steer 主人发起的回合，否则等于让别人借用主人的权限（依据：openclaw-architecture §2.2 Q2、§5 坑 9）。
- **中断时丢掉 CLI 还没读到的 steer**，否则刚停掉的回合会被它重新拉起（依据：paseo-architecture §2.2 Q4）。
- **邮箱有上限，溢出时写摘要，不静默丢弃**；每个邮箱记"最后一次被消费的时间"并监控，防止队列坏了好几天没人发现（依据：openclaw-architecture §2.2 Q2"队列上限 20、溢出时摘要"；companion-architectures §9 坑 18）。

**〔新提议 N5〕主人的消息抢占非主人发起的回合。** OpenClaw #30197：用户消息被 steer 进正在跑的 heartbeat 回合，模型先回了 `HEARTBEAT_OK`，对用户的真实回复被一起吞掉（依据：openclaw-architecture §8.1.2"主动消息打扰人"一行）。灵鲸的结构隔离（§8）已经降低了"吞掉"的可能，但混在一个回合里，弱模型仍可能顾此失彼。所以：主人的消息到达时，如果主意识正在跑通知或自主触发的回合，而且这个回合还没产生副作用，就在下一个安全点中断它，把它用到的通知放回收件箱（未消费），先跑主人的回合；如果已经产生了副作用，就让它跑完，再跑主人的回合。"有副作用就不重来"这条规则取自 AIRI（依据：companion-architectures §4.2 Q3）。

### 5.2 通知格式

通知是"简短事件"，不是想法汇总（依据：决策 13①；companion-architectures §9 坑 1）。内容分两层：一两句话的摘要，加一个报告引用；完整内容存在本体里，主意识需要时用 `get_report` 取（依据：papers-architecture §3.3 13-1）。字段取自 CTM 的 chunk（来源、时间、要点、权重）并补上灵鲸需要的受众（依据：papers-architecture §2.2 CTM、§6 B）。

| 字段 | 含义 |
| --- | --- |
| 编号 | 去重和"至少送达一次"用 |
| 来源 | 哪个会话、作业或模块产生的 |
| 时间 | 事件发生时间 |
| 类别 | 见下表 |
| 紧急度 | immediate、soon、later 三档（依据：companion-architectures §4.2 Q3，AIRI spark:notify） |
| 摘要 | 一两句话 |
| 报告引用 | 详细内容在本体里的位置，例如任务进度摘要、请求详情 |
| 相关对象 | 任务、真人、场合的编号，给预取和关注清单匹配用 |
| 原消息号 | 需要原话时，由本体按编号从日志取原文 |
| 受众 | 这条通知内容本身的受众；主意识能看全部，但转话时要按它处理 |
| 去重键 | 同一件事多次发生时合并计数 |

通知以带来源属性的结构块进入主意识，正文做转义；人发的消息如果长得像这种结构块，会被转义成普通文本，防止有人伪造"系统通知"（依据：paseo-architecture §2.2 Q9 上游 agent-messages 信封）。

| 类别 | 谁产生 | 默认紧急度 | 能否突破 |
| --- | --- | --- | --- |
| 主人在别处的动作（主人直连分身、主人在群里说话） | gateway、gate | soon | 否（主人私聊本身走突破通道，不是通知） |
| 活的里程碑：设计已交、阻塞提问、完成、失败 | tasks | soon | 否 |
| 需要全局决定【V2】 | 在场分身 | soon | 否 |
| 关注命中 | mind（代码匹配） | 按关注项设定 | 按关注项设定 |
| 自主触发 | scheduler | later | 否 |
| 场合里的要紧事：被问到主人、可疑的操控【V2】 | 在场分身、gate | soon；安全类 immediate | 安全类可以 |
| 系统：大脑降级、总闸变化、适配器离线、结果不明的动作 | guard、brains、procs、actions | soon | 否 |

### 5.3 收件箱的进入规则与关注清单

全局工作空间理论（GWT）给出了结构上的解释：决定什么能进中心的，一是外围过程自己报的显著性（自下而上），二是中心当前的目标（自上而下）；足够重要的信号能突破当前的专注（依据：papers-architecture §2.2）。这里只借它的结构解释，容量上限的理由来自上下文退化和成本（依据：papers-architecture §8.1 第 1 条、§2.4 E2）。

| 规则 | 做法 | 依据 |
| --- | --- | --- |
| 合并 | 同一来源 2 秒安静窗口内的多条合成一次投递 | paseo-architecture §2.2 Q9 |
| 淡出 | 同一去重键的重复事件合成一条加计数 | papers-architecture §2.2（重复信息因习惯化淡出） |
| 排序 | 类别默认紧急度（自下而上）+ 关注清单命中（自上而下） | 决策 13①；papers-architecture §3.5 修正 A |
| 配额 | 每轮最多 K 条进上下文，其余留在收件箱，前缀里写"另有 N 条待看" | papers-architecture §2.2（工作空间容量有限）、§2.4 E2 |
| 消费 | 回合成功结束才标记已消费；回合失败或被抢占，通知留着下次再投 | paseo-architecture §2.2 Q9（至少一次投递） |
| 突破 | 只有三类能打断主意识正在跑的回合：主人的消息、需要主人审核的高风险事件、安全事件 | 决策 13①；papers-architecture §3.3 13-2 |

**关注清单。** 主意识用 `watch(匹配条件, 效果, 能否突破, 到期)` 登记，例如"在等妈妈回话" → `watch(真人 = 妈妈, 效果 = 立即, 到期 = 今晚)`。匹配条件只能是代码能判断的东西：真人、任务、场合的编号，通知类别，关键词；效果是提高紧急度或暂时压下；每项必须有到期时间，总条数有上限。匹配由代码做，不由模型做（依据：决策 13①；papers-architecture §3.5 修正 A）。"按主意识处理或忽略的记录调整规则"这一可选项不进第一版，以后要做也必须经主人确认（依据：papers-architecture §3.3 13-2 可选项）。

### 5.4 决定往下传（广播）

- 主意识用 `decide(内容, 适用范围, 受众, 到期, 理由)` 定方针，用 `commit` 记承诺；两者都写进 agenda，她的状态版本加一（依据：决策 13②）。
- 每个会话记住自己上次看到的版本。下一轮开头，context 调 `agenda.changesSince(版本, 本会话受众, 本会话范围)`，把变化作为一条提醒放进本轮前缀；不打断正在跑的回合（依据：决策 13②；papers-architecture §3.5 修正 A）。不打断的理由是：打断会让手上的事偏航，GWT 的广播也是给各模块下一次处理用的（依据：papers-architecture §2.2）。
- 提醒走 user 角色的提醒块，不插 system 消息。Letta 给出的理由是：Anthropic 会拒绝出现在普通 assistant 消息之后的 system 角色通知（依据：companion-architectures §3.2 Q6、§7.1）。
- 广播同样按受众过滤：方针和承诺本身带受众，在场分身只收到它的受众能知道的部分。主意识定给在场分身看的方针，要写成那个受众能知道的说法（依据：决策 12"只拿在场者都有资格知道的记忆"；companion-architectures §7.2 eliza v2 受众准入）。
- 当下状态的变化也走同一条提醒；成长版本的变化只在新会话生效，因为它在系统提示里，会话创建后就固定了（依据：companion-architectures §3.2 Q1"记忆改动只在下一个会话生效"、§7.5）。
- 会话中途注入提醒在 Claude Code 和 Codex 上的表现要实测（§16 第 2 条）。

### 5.5 派活交接包

| 字段 | 内容 | 谁提供 | 依据 |
| --- | --- | --- | --- |
| 原话 | 主人的原话，按消息号由本体从日志取原文 | 代码 | 决策 5、14；papers-architecture §3.2 12-6 |
| 相关聊天 | 主意识指定消息号范围，本体取原文 | 主意识选范围，代码取 | 决策 14 |
| 主意识到目前为止的决定和理由 | 例如"主人说先别动支付部分" | 主意识 | 决策 14；papers-architecture §3.5 修正 C |
| 分身不知道什么 | 明确列出，例如"主人上周换了服务器，旧地址作废" | 主意识 | 决策 14；papers-architecture §2.5 E5（"agent 以为和子 agent 共享状态，其实没有"） |
| 相关记忆 | 和这件活相关、主人能知道的记忆 | 代码（memory.recall） | product.md「主意识、分身与朋友」 |
| 汇报格式 | 固定的进度摘要格式 | 任务模板（代码） | 决策 14；papers-architecture §2.5 E1 |
| 边界 | worktree、花费上限、不许联系别人、不许动的目录 | 模板默认 + 主意识补充 | 决策 14；papers-architecture §2.5 E1 |
| 审核点 | 默认"设计 → 主人审设计 → 执行 → 主人验收"，主意识可以加 | 模板 + 主意识 | product.md「干活」；决策 14 |
| 回问通道 | 用 `ask` 问主意识；涉及主人决定的转给主人 | 模板 | 决策 14；papers-architecture §2.5 MAST（"该问不问"占 6.8%） |
| 执行者和大脑 | 从代码给出的候选里选：她的分身配哪个大脑，以后还可以是某个朋友 | 主意识选，代码给候选 | 决策 6；papers-architecture §3.4 |

三条规则：

1. **交接包只补流程，不改写需求。** 需求的理解和方案设计由分身完成（依据：决策 5、14）。
2. **派活是一个带结构化参数的工具调用，执行者从候选清单里选。** 主人明说"让某某做"时由代码直接路由。弱模型靠提示词当编排者有明显偏差（依据：papers-architecture §3.4、§2.6 ToolOrchestra；§2.5 E3 防错设计）。
3. **派活带幂等键。** 重试不会派出两件一样的活；结果不明时返回"结果不明"，不重复执行（依据：paseo-architecture §3"创建日志"一行）。

### 5.6 共享状态单点写

在场分身、干活分身互不共享上下文，冲突不在说话风格，而在共享状态上（依据：papers-architecture §3.2 12-4）。所以这些状态只能经本体 API 写入，由所有者模块做冲突检查；写入保持单线程（依据：决策 12；papers-architecture §2.5 E5"写入保持单线程"、§2.2 BIGMAS"每次写入都要校验"）。

| 共享状态 | 所有者 | 写入 API | 冲突检查 | 谁能直接写 | 谁必须提请 |
| --- | --- | --- | --- | --- | --- |
| 承诺（含对外答应的事）、日程 | agenda | `commit` | 和已有承诺、作息、主人日历【V4】的时间冲突 | 主意识 | 在场分身【V2】；干活分身不对人许诺，只汇报 |
| 方针 | agenda | `decide` | 和现有方针矛盾时提示 | 主意识 | 在场分身 |
| 关于她自己和主人的事实 | memory | `note`、`propose` | 同一主体同一属性的已有事实是否矛盾 | 主意识；内省会话交提案 | 在场分身 |
| 关系变化、印象 | social | `propose` | 主人设定的关系不可改 | 内省会话交提案；主人 | 在场分身 |
| 同一工作区的文件 | workspace | 写租约 + worktree | 同一 worktree 只有一个写入会话；合回主线时暴露冲突 | 持有租约的干活分身 | — |
| 当下状态 | persona | `feel`（作为输入） | persona 自己的规则 | 只有 persona | — |

冲突检查的结果只有三种：接受、带理由拒绝、需要主意识决定。

### 5.7 在场分身提请全局决定【V2】

**"全局决定"用清单定义**，不留给分身自己判断（依据：papers-architecture §3.2 12-2"'全局决定'没有定义"、§3.5 修正 B）：

- 对任何人许诺、约时间；
- 关于她自己和主人的新事实陈述；
- 关系的变化；
- 涉及主人隐私或主人利益的回答；
- 任何花钱或对外不可逆的事。

流程：

1. 在场分身调用 `request_global_decision(类别, 问题, 原消息号, 建议答复, 期限)`。
2. 她在场合里用自己的口吻先稳住，例如"我问问""等我想想"，不替主意识做决定。
3. mind 生成通知进收件箱；主意识回合里用 `commit`、`decide` 或直接驳回。
4. agenda 版本加一；在场分身下一轮开头收到提醒，在场合里给出答复。
5. 到期限还没定，在场分身收到"还没定"的提醒，继续稳住；它永远不自己拍板。

### 5.8 主人直连分身

- 主人在主控台打开任何一个会话（干活分身，第二版起也包括在场分身），在里面说话：消息直接进那个会话，来源标"主人直连"；干活分身里默认 steer，"叫停"是 interrupt；主人还可以暂停、换大脑（换大脑 = 用新大脑开新会话，从日志重建上下文）（依据：product.md「主意识、分身与朋友」；paseo-architecture §3）。
- 主意识收到一条低紧急度通知"主人直接和分身 X 说了：…"，让状态表保持准确；这段经历照样汇进她的记忆，来源标"主人直连"（依据：client-backend §3.6"主人直连分身不经主意识，但经历仍汇入她的记忆"）。
- 直连只在主控台。主人从 QQ 等形态说的话一律进主意识，由主意识把原话转过去（见 §17.2 C4）。

### 5.9 权限请求、子会话、叫朋友

- **权限请求。** 分身 CLI 的原生权限请求，白名单内的（本 worktree 内读写、跑项目脚本）自动放行；其余作为注意力事件直接交主人，主意识只负责提醒，不代批。主意识的大脑是便宜模型，让它替主人做安全决定不合适（依据：paseo-architecture §3、§5 坑 3；papers-architecture §7.2）。内省会话是无人值守运行，遇到任何权限请求直接算失败（依据：paseo-architecture §3"unattended"一行）。
- **子会话。** 干活分身用 `spawn(执行者, 交接包)` 开子会话，执行者只能是她的分身或朋友；深度和并发有上限；子会话的经历记在所属任务名下，结果回父会话，不进主意识（依据：决策 5；openclaw-architecture §2.2 Q3；paseo-architecture §2.2 Q4）。
- **叫朋友【V3】。** 交接包同上，执行者是朋友：用朋友的人设、朋友的记忆。两边各记各的：她这边记"我请老师做了什么、结论是什么"，老师那边记成自己的经历，来源标"闺女"。叫醒朋友不看预算（依据：product.md「主意识、分身与朋友」「记忆」；openclaw-architecture §3"每个 agent 有独立的工作区"一行；决策 9）。

| `submit(种类, 结构化内容)` | 交记忆提案、日记、成长提案、明日材料 | — | — | — | ✓ |
| CLI 原生工具（读写文件、shell） | 干活 | — | — | ✓（限本 worktree） | — |

内容段包括文字、语音（按句带情绪意图）、表情包、现成图片【V1 后期】，自己画的图【V2】。语音的情绪走工具参数，不让大脑在正文里写各家私有标签：这样能校验格式，也不会污染文字渠道（依据：ability-plugins §3.2）。

## 6. 事实来源与持久化

### 6.1 日志是唯一事实来源

做法叫**事件溯源**：每件发生过的事作为一条不可改的记录追加进日志，"当前状态"都是从日志算出来的投影。

为什么这样定：

- product.md 写明"记忆唯一来源是每个数字生命自己的操作日志"，成长要"可查、可回滚"，主人要能看到"她最近变了什么、为什么变"。只有保留全部经过，才回答得了"为什么"（依据：product.md「记忆」「数字生命由什么组成」）。
- CoALA 按"能不能控制"划分内外：本体控制不了 CLI 转录的格式和保留策略，所以 CLI 转录对灵鲸来说属于外部（依据：papers-architecture §2.1）。
- Auto-Dreamer 的局限写着"写入时漏掉的信息，巩固器通常找不回来，除非原始轨迹让它显眼"：原始日志必须一直保留，整理不能覆盖它（依据：papers-architecture §2.4）。

放弃的方案：

- **以 CLI 转录为真相**（Paseo）：Paseo 自己产生、转录里没有的东西（插件行、系统注入消息、错误行、完成订阅）重启就丢；换 CLI 就等于换了一份真相（依据：paseo-architecture §2.2 Q5、§5 坑 1）。
- **以状态表为主**（OpenClaw、麦麦）：OpenClaw 的会话、作业、人格、记忆分散在几个 SQLite 和 Markdown 里，审计只记元数据，没法从日志重建记忆和人格（依据：openclaw-architecture §3"没有统一的事件日志"一行、§4 第 6 条；companion-architectures §2.2 Q8）。
- **两份并列的真相**（Letta：会话 jsonl 加记忆 git 仓库）：两边可能对不上，记忆没法从转录重建（依据：companion-architectures §3.2 Q8）。

### 6.2 事件信封与流

每条事件的字段沿用 client-backend §3.2 的表结构：全局位置、流类型、流编号、流内序号、类型、版本、执行者、发生时间、因果号（这条事件是由哪条引起的）、关联号（属于哪一串事）、来源信息、内容。同一条流里的序号唯一，追加时带"期望序号"，序号对不上就说明有人先写了，这是单点写入做冲突检查的底层手段（依据：client-backend §3.2）。

**来源信息**第一版就写全（依据：client-backend §3.2）：

- 场合、参与者快照的引用、受众；
- 来源人、可信度：主人、成员、绑定的真人、陌生人、系统、网络内容；
- 污染标记：读过网络内容的那一轮，之后的输出都标为不可信（依据：openclaw-architecture §2.2 Q6 taint）。

来源信息存在独立的列里，模型没法通过改写正文改掉它（依据：openclaw-architecture §2.2 Q6）。

**流的划分：**

| 流 | 装什么 |
| --- | --- |
| 成员流 `member:<id>` | 她的状态变化：当下状态、成长、承诺、方针、记忆变更 |
| 会话流 `conversation:<id>` | 回合、消息、工具调用、用量 |
| 场合流 `occasion:<id>` | 场合里收到的消息，包括没唤醒她的 |
| 任务流 `task:<id>` | 阶段流转、交接包、汇报、核验结果 |
| 系统流 `system` | 暂停、总闸、配置、作业、进程事故 |

**哪些进日志：** 消息完成、工具调用完成（输出有上限）、阶段流转、用量、快照、记忆变更。**哪些不进：** 逐字吐出的增量、工具执行中的进度，这些只走实时推送，在条目完成时一次性提交（依据：client-backend §3.2）。工具输出、diff、图片、语音这类大对象按哈希存进 `blobs/`，事件里只放引用（依据：client-backend §3.2）。

进程登记、订阅游标、连接这类**运行时的操作数据**不是"她的事实"，是各模块自己的表，不进日志。

### 6.3 投影

| 种类 | 例子 | 怎么更新 | 存在哪 |
| --- | --- | --- | --- |
| 内联投影 | 时间线、会话列表、任务看板、状态表、收件箱、承诺与日程、作业、花费汇总 | 和追加事件在同一个事务里更新，读到的永远是最新的 | liwa.db |
| 异步投影 | 记忆、全文检索索引、向量索引、日记、成长视图 | 各自记"处理到哪条日志"的检查点，按批追上 | derived.db〔新提议 N6〕 |

所有投影都可以删表、从日志重放重建，重建本身也是迁移手段（依据：client-backend §3.2）。

**〔新提议 N6〕异步投影单独放在一个可重建的库文件里。** 异步投影和索引体积大、重建频繁；放在单独的文件里，重建、索引膨胀、WAL 变大都碰不到装真相的那个文件，备份也只需要备 liwa.db 和 `blobs/`。OpenClaw #143524 里，一个 agent 的 WAL 文件两天涨到 1.4–2.8 GB，网关进程活着却始终不绑端口（依据：openclaw-architecture §8.1.1）。代价是两个库之间没有跨库事务，但异步投影本来就是"稍后追上"的，不需要。

### 6.4 CLI 转录的位置

- Claude Code、Codex 自己存的转录只是**续接用的缓存**。本体从不把它读回来当真相；新开会话、换大脑时，上下文都从日志重建。读 CLI 历史只用在导入外部会话和核对（依据：paseo-architecture §3"timeline 只在内存"一行）。
- 每个成员的 CLI 数据目录放在本体的数据目录下（§3.4），这样主人删除或抹掉某段内容时，本体能连带删掉或轮换受影响的 CLI 会话文件。Codex 即使在"无痕"会话里也照写诊断日志，`persistSession:false` 是空操作，所以隐私和删除必须覆盖到 CLI 那一侧（依据：openclaw-architecture §5 坑 10；paseo-architecture §5 坑 11）。Claude Code 能否把数据目录指到指定位置要实测（§16 第 8 条）。

### 6.5 副作用协议：先记"将要做"

```
effect.intended（带幂等键）──执行成功──▶ effect.completed
        │                    └─执行失败──▶ effect.failed{类别, 能否重试}
        └─本体在中间崩溃──▶ 重启时补记 effect.unknown
```

| 规则 | 做法 | 依据 |
| --- | --- | --- |
| 先记后做 | 任何有外部后果的动作（发消息、派活、建作业、调收费服务）先写"将要做"，再执行，再写结果 | companion-architectures §5.2 Q8（eliza v2"Persist a dispatch transition before any effect"）、§7.6 |
| 结果不明不重放 | 重启时，有"将要做"没有结果的记为结果不明；不自动重放；能只读核对的就核对（例如向平台查这条消息发没发出去）；核对不了的变成系统通知给主意识，涉及主人的同时告诉主人 | companion-architectures §2.2 Q1（麦麦"禁止自动重放"）、§5.2 Q8（eliza"对账只读取证，不重做"）；openclaw-architecture §7 J（投递结果不明时在下一轮提示） |
| 重试用同一个幂等键 | 同一进程内的重试带同一个幂等键，让对方去重。**幂等**指同一个请求做一次和做多次效果一样 | openclaw-architecture §2.2 Q1（有副作用的方法必须带幂等 key）；paseo-architecture §3"创建日志"一行 |
| 被打断的回合 | 有开始没结束的回合补记 `turn.interrupted`。主人发起的回合，重启后在续接的会话里发一条续跑提示，写明哪些动作已完成、哪些结果不明、不能当作已执行；续跑有次数预算，续跑前重新确认发起者的权限。后台和作业的回合记失败，按作业策略重排 | client-backend §3.2；openclaw-architecture §7 J；companion-architectures §2.2 Q10（麦麦"上一轮未完成"提示）；paseo-architecture §2.2 Q6 |

### 6.6 记忆和成长怎么从日志里长出来

这里只讲架构位置，算法留给记忆和成长两个模块（依据：papers-architecture §5.3 的分层表）。

| 层次 | 写到哪 | 怎么产生 | 触发 | 依据 |
| --- | --- | --- | --- | --- |
| 情景记忆 | 日志本身 | 每个事件就是一条经历 | — | papers-architecture §2.3（Generative Agents 记忆流）、§5.3 |
| 事实、关系记忆 | memory 投影 | 内省会话读"上次检查点之后"的日志片段，交抽取提案；memory 校验后写成记忆事件 | 按条数或时间批量、会话换新前、白天空闲时 | papers-architecture §5.3；companion-architectures §7.4（Letta V1、eliza 的检查点；麦麦每条一次太贵） |
| 反思 | memory 投影（反思也是记忆，带证据指针） | 内省会话 | 重要度累计、会话换新时、每晚 | papers-architecture §2.3 |
| 跨会话巩固 | memory 投影的新版本，原始日志不动 | 夜间内省会话 | 每晚 | papers-architecture §2.4 Auto-Dreamer |
| 成长 | persona 的成长版本 | 只在夜间巩固时提案；要有跨多个会话、多种来源的重复证据；按来源加权，非主人来源不能单独促成成长；persona 按规则校验后生效；下个会话生效；可回滚 | 每晚 | papers-architecture §5.3（CoALA：改程序记忆风险最高；GA §7.2 过度合作；P16 长对话会采纳对方指令）；companion-architectures §7.4（Letta"凭模式不凭单次事件"）；product.md「人设」（成长不改底色） |
| 日记 | 日志 → 投影 | 夜间内省会话 | 每晚 | product.md「自己生活、学习与成长」 |
| 技能【V4】 | skills | 活经过验证（主人验收或测试通过）后才成为候选 | 任务完成 | papers-architecture §5.3（CoALA 引 Voyager） |

**写进记忆之前先清洗。** OpenClaw 出过两类事故：控制 token 和没解析的工具调用被存进每日记忆，下次作为摘要再注入，输出越来越坏（#69943）；一个 agent 陷入工具调用循环，别的 agent 读了那段转录也开始循环（#113346）。所以抽取前要去掉控制 token、没解析的工具调用和重复循环的片段；本轮注入进去的内容（召回的记忆、人设）做结构标记，不会被再抽一遍；来源是系统或不可信的内容不能被提升（依据：openclaw-architecture §2.2 Q6、§8.1.2、§8.1.3 第 4 条）。

**成长对主人可见。** "她最近变了什么、为什么变"就是成长事件的投影，每条带证据指向的日志（依据：product.md「自己生活、学习与成长」"成长日记"）。

### 6.7 更正、删除与"日志只追加"

- **更正**：写一条记忆更正事件，投影照着改；原来的记录还在，可以审计。
- **删除**：写一条记忆删除事件，投影里不再出现；重建时也照样不出现。
- **真正抹掉〔新提议 N7〕**：主人要求某段内容彻底消失时，用 `journal.redact(事件号, 理由)` 把那些事件的内容替换成墓碑（保留信封，抹掉正文），写一条脱敏事件记录这件事；重建受影响的投影，删掉相关的大对象，删除或轮换含有它的 CLI 会话文件。这是日志唯一允许的改写，只有主人能发起。脱敏之前做的备份里仍有原文，要告诉主人。
  - 为什么需要：product.md 同时要求"记忆唯一来源是日志"和"主人可以删除任何一条记忆"。只有上面两种事件的话，"删除"其实只是"隐藏"，原文还在日志里（依据：product.md「记忆」）。
  - 对照：OpenClaw 的转录只追加，编辑或删除消息不改写旧行（依据：openclaw-architecture §2.2 Q9）；CLI 那一侧的副本也要覆盖到（依据：openclaw-architecture §5 坑 10）。

### 6.8 存储布局与备份

| 位置 | 内容 |
| --- | --- |
| `liwa.db` | 日志 + 内联投影 + 各模块的操作数据表 |
| `derived.db` | 异步投影、全文索引、向量索引；可删掉重建〔新提议 N6〕 |
| `blobs/` | 大对象，按哈希命名 |
| `members/<id>/cli-home/` | 各 CLI 的数据目录（缓存） |
| `conversations/<id>/` | 非干活会话的私有工作目录；CLI 一定要有工作目录，ACP 用的人设指令文件也放这里（依据：paseo-architecture §2.2 Q2、§3"独立对话"一行） |
| `workspaces/` | 项目、每件活的 worktree、快照 |
| `trash/` | 回收站 |
| `backups/` | 备份 |

- **启动自检**：SQLite 版本不低于 3.51.3（更低的版本有 WAL 重置损坏的问题），NUL 字符往返测试，Node 版本检查（依据：client-backend §4 坑 2）。**WAL** 是 SQLite 的预写日志文件，需要定期合并回主库；合并（checkpoint）由 journal 负责，并监控 WAL 大小（依据：openclaw-architecture §8.1.1 #143524、§8.1.3 第 5 条）。
- **备份**：node:sqlite 的 `backup()` 备份 liwa.db，加上 `blobs/` 和配置；derived.db 和 CLI 数据目录可以不备，因为能重建（依据：client-backend §3.2）。
- **搬家**：新机器上恢复备份 → 重建 derived.db → 会话从续接句柄续接，续接不了就从日志重建（依据：product.md「规矩」"备份与搬家"）。
- **保留**：日志不自动清理，原始经历要一直在（依据：papers-architecture §2.4 Auto-Dreamer）。mac mini 内置盘只剩约 23 GB，所以大对象设上限、工具输出截断，磁盘用量在主控台可见（依据：early-findings §4；paseo-architecture §2.2 Q3 工具输出截到 64 KiB）。

## 7. 主动性与生活循环

### 7.1 统一作业模型，不设心跳

OpenClaw 用了半年、几百条 issue 才把 heartbeat 拆回普通定时任务：七套自动化机制重叠，heartbeat 和 cron 是两个调度者，`HEARTBEAT.md` 是"调度器里的调度器"，节奏在作业列表里看不见；标题含 heartbeat 的 issue 有 879 条，大量是节奏失灵、跑到别的会话、内部输出外泄、吞掉用户回复（依据：openclaw-architecture §8.2、§8.1.2）。Paseo 的 heartbeat 也只是 schedule 的一种目标（依据：paseo-architecture §2.2 Q6）。所以灵鲸从第一天起，作息、闲时、承诺到期、每晚整理都是同一种**作业**，按属性区分。

| 字段 | 取值 | 依据 |
| --- | --- | --- |
| 触发 | cron 表达式；一次性时刻；间隔；"空闲满 N 分钟"（主人空闲或她空闲）；事件：主人回来了、某个形态有新观察【V4】、承诺到期、日志条数到阈值 | companion-architectures §4.2 Q4（AIRI 的触发种类）；papers-architecture §2.4（MemGPT 把"用户登录"当事件） |
| 目标 | 以通知唤醒主意识；开一个内省会话；本体直接执行（例如换新会话、备份） | paseo-architecture §2.2 Q6（新建对话和唤醒已有对话两种目标）；companion-architectures §3.2 Q4（Letta cron 的目标会话） |
| 活跃时段 | 来自作息 | openclaw-architecture §2.2 Q5 `activeHours` |
| 只在空闲时 | 主意识或主人空闲才跑；忙就等，不算失败 | openclaw-architecture §2.2 Q5 `idleOnly`；paseo-architecture §5 坑 4 |
| 补跑 | 不补或补一次：承诺类补，巡检类不补 | paseo-architecture §5 坑 5；openclaw-architecture §2.2 Q5 |
| 冷却与上限 | 两次之间的最短间隔、每日上限 | companion-architectures §4.2 Q4；papers-architecture §2.7 Need Help |
| 看门狗 | 运行超时就中断、记失败 | openclaw-architecture §2.2 Q5（60 分钟） |
| 出错停用 | 连续出错自动停用，并通知主人 | openclaw-architecture §2.2 Q5 |
| 大脑 | 可以单独指定 | openclaw-architecture §2.2 Q5 |
| 两道闸 | `shouldRun`（调度侧，不加载上下文）和 `canExecute`（执行侧，带完整上下文） | companion-architectures §5.2 Q4 |

- 作业存在 SQLite 里，只用一个定时器等"下一次最近的触发"；机器睡眠期间错过的多次触发合并成一次（依据：openclaw-architecture §2.2 Q1 GatewayScheduler）。不每秒扫一遍全部作业（依据：paseo-architecture §5 坑 6）。
- **自主开关关闭的成员不建任何自主触发作业**，这就直接满足了"只有开启自主的成员持续消耗 token"（依据：product.md「自主开关」；openclaw-architecture §3"heartbeat 退役"一行）。
- **"睡觉"只停自主触发作业。** 主人的消息、别人的私聊、群里点名、分身手上的活都照常（依据：决策 10；product.md「作息」）。

### 7.2 默认不说话

对外发言只能经工具（§8），所以一个没有调用对外工具的回合就是安静的，记成 `turn.completed{安静}`，不需要模型额外输出 `NO_REPLY` 之类的暗号。OpenClaw 靠模型记得输出 `NO_REPLY`，issue 作者说这"fragile and fails regularly"（依据：openclaw-architecture §8.1.1 #25592、§8.1.3 第 1 条；决策 11"没话可以不说"）。Letta 的做法相同：agent 不调 `MessageChannel` 就等于不回（依据：companion-architectures §3.2 Q3）。

### 7.3 开口找主人的三道闸

| 闸 | 做什么 | 依据 |
| --- | --- | --- |
| 1. 代码触发 | 作业的触发条件命中 | papers-architecture §5.2 第 1 条；companion-architectures §4.2 Q4 |
| 2. 频率与情境 | 每日主动上限、两次最短间隔、主人日历显示忙【V4】、主人最近几次没理睬就退避、主人正在和她聊天就不另起主动 | papers-architecture §2.7 Need Help（建议太频繁，偏好从 90% 跌到 47%）、ProactiveBench（模型误报 50%–65%） |
| 3. 模型判断 | 可以安静返回；想清楚"有没有值得说的" | papers-architecture §2.7 Inner Thoughts、§5.1 |

- **"自己做事"和"开口找人"分开。** 自己逛、自己学、做工具【V4】不打扰任何人，只受作息和花钱总闸约束；开口找主人才过这三道闸（依据：papers-architecture §5.2 第 1 条）。
- **目标是主人的接受率，不是主动的次数。** 主人不需要时保持沉默也算对（依据：papers-architecture §2.7 ProactiveBench、§5.2）。默认阈值取"积极贡献者"一档：阈值太高显得冷淡，Inner Thoughts 的用户研究里"只在很感兴趣时才说话"的一档被评为最差（依据：papers-architecture §2.7）。

### 7.4 空闲整理与睡觉换新

- **白天空闲**满 N 分钟：跑增量抽取作业（内省会话）。
- **到了睡觉时间，而且主意识空闲**：跑夜间作业链：跨会话巩固 → 成长提案 → 写日记 → 备好明天的材料（早安要说的事、到期的承诺、没做完的活）→ 主意识换新会话。主人到了睡觉时间还在聊，就推迟到空闲。
- **上下文压力**（例如用到七成）：空闲时也可以换新；换新前先把要紧的内容写回日志和记忆（依据：papers-architecture §2.4 MemGPT 的内存压力警告；openclaw-architecture §2.2 Q6 压缩前写回记忆）。
- **换新**：新会话注入人设、当下状态、交接摘要、召回记忆，以及从日志取的最后 N 轮原文，让主人感觉不到换了会话（依据：决策 13⑤；papers-architecture §3.3 13-5）。
- **夜间用什么大脑**：夜里不在乎延迟，按决策 6 由实测决定是否换更强的模型（依据：决策 6；papers-architecture §3.3 13-6、§8.1 第 9 条）。

整体依据：决策 13⑤；papers-architecture §3.5 修正 E、§2.4（sleep-time compute 说的是任何空闲时间；Auto-Dreamer 离线巩固）。

### 7.5 承诺

- `commit` 一次性建好承诺和对应的作业，作业一建就启用。OpenClaw 的教训是：停用状态下等确认的作业谁也看不见，是更糟的失败（依据：openclaw-architecture §2.2 Q5"Promised Work"、"升级成定时作业"）。
- 承诺记录写清原始请求，例如"主人让我明天上午提醒他交房租"，而不只写"提醒"（依据：companion-architectures §3.2 Q4，Letta cron 提示词要写清原始请求）。
- 到期时通知主意识，由她用自己的口吻兑现（依据：product.md「干活」"兑现承诺"）。
- 本体重启错过的承诺要补跑（依据：paseo-architecture §5 坑 5）。
- 写入时由 agenda 做冲突检查（§5.6）。
- 主人反复要求的同一件事，由主意识提议变成定时作业；主人确认后直接以启用状态创建，并立刻试跑一次（依据：openclaw-architecture §2.2 Q5；companion-architectures §4.2 Q4 AIRI 的提案）。

### 7.6 生活从哪来【V4】

本稿只定方向：她的"生活"由真实可执行的事组成，例如承诺、主人日历、按兴趣在某个形态上能做的事；模型负责排序和分解，不编一段日程叙事。麦麦每天用模型写 1500 字日程，0.7 以"减少幻觉"删掉，至今没回归；Generative Agents 又证明没有计划会在中午连吃三次午饭。两者不矛盾：计划要有，但要落在真实的事上（依据：companion-architectures §2.2 Q4、§7.3；papers-architecture §5.2 第 2 条）。自己找事做的具体机制留给成长模块。

### 7.7 反馈闭环

主人对每次主动的反应（回复、点开、忽略、"别烦我"）写进日志；阈值和每日上限的调整做成主人可见的配置变更事件（依据：papers-architecture §5.2 第 3 条；§2.7 Need Help"参与者希望能自己选择开关和频率"）。

## 8. 对外发言与行动的结构隔离

### 8.1 OpenClaw 的两个痛点

1. **内部内容漏给用户。** 工具调用之间的叙述、报错、对系统事件的确认被当成消息发到 Slack 和 iMessage（#25592）；每轮注入的内部上下文块以可见文本出现在 Telegram 里（#137927）；升级后 heartbeat 的内部输出直接发到用户私聊（#143278）；内部字符串被当成"用户消息"交给模型，又没写进转录（#151962）。根源是 OpenClaw 默认把模型的原始文本发到渠道，内部上下文、系统事件又以文本拼进用户这一轮（依据：openclaw-architecture §8.1.3 第 1 条）。
2. **投递目标是会被改写的会话状态，结果发错人。** 一个非管理员员工私聊了一句，覆盖了 main 会话的回复目标，之后 heartbeat 把财务数字和安全告警发给了他（#24148）；一条 cron 结果 9 分钟后被重放，用了早先一个无关工作流留下的路由，发到错误的频道（#135117）；还有 #99912、#79308。根源是"会话记着最近一次的回复目标"（依据：openclaw-architecture §8.1.3 第 2 条）。

### 8.2 结构规则

| # | 规则 | 防的是什么 | 依据 |
| --- | --- | --- | --- |
| R1 | **模型的原始输出一律算内部。** 只有对外工具（`reply`、`sayToOwner`、`relay`，以及其中的语音、表情包、图片段）会产生对外内容。原始输出只进日志，主人可以在日志页查看 | 痛点 1 | openclaw-architecture §8.1.3 第 1 条；companion-architectures §3.2 Q3（Letta 必须调 `MessageChannel`）、§2.2 Q1（麦麦必须调 `reply`）；papers-architecture §2.2 GWA 的 Response 节点 |
| R2 | **每个对外动作都带明确的收件人。** 收件人只有三种来源：一个事件号（目标就是那条事件所在的场合，由事件带来）；主人；一个明确指定的真人。系统里不存在"会话的上次回复目标"这种状态 | 痛点 2 | openclaw-architecture §8.1.3 第 2 条 |
| R3 | **主意识只直接对主人说话。** 对其他人，主意识用 `relay` 托目标场合的在场分身转话，正文由在场分身在目标场合的上下文里生成 | 跨场合泄露 | 决策 11"别人不直接接触主意识"；companion-architectures §7.1（麦麦 Replyer"只看目标聊天历史 + 指导"） |
| R4 | **执行处检查目标。** 在场分身只能对自己的场合说话；主意识只能对主人的场合说话；指定真人时只按主人绑定的身份解析，永远解析不到别人身上；成员快照过期按最严受众处理 | 痛点 2；冒充 | companion-architectures §5.2 Q2（eliza v2 成员权威、owner_bound）；papers-architecture §6 I |
| R5 | **内部输入走独立的结构通道。** 通知、广播提醒、自主触发以带来源属性的结构块进入会话，绝不拼成"主人说"；人发的消息如果长得像结构块，会被转义成普通文本 | 痛点 1；伪造系统消息 | paseo-architecture §2.2 Q9（agent-messages 信封）；openclaw-architecture §8.1.2（#151962、#30197） |
| R6 | **出站清洗。** 投递前去掉控制 token、内部标签、工具调用残留 | 痛点 1 | openclaw-architecture §2.2 Q8 |
| R7 | **系统确认不进对外场合。** "作业已创建""设置已更改"这类只在主控台显示 | 刷屏 | openclaw-architecture §8.1.2（#68478） |
| R8 | **错误文案只从一处出。** 错误类别映射到她口吻的固定说法；同一事故在同一场合只说一次；外部场合出错默认沉默；兜底文案带标记，不回流进上下文和记忆。花钱总闸拉下时她不知道，所以不会用"没钱了"之类的话解释，主人在主控台看到系统状态 | 原始报错外泄；兜底刷屏污染上下文 | product.md「规矩」"出错也像人"；companion-architectures §3.2 Q7（Letta"Never post raw internal errors to a channel"）；openclaw-architecture §8.1.2（#116348）；决策 9 |
| R9 | **自己的消息回流时标记为"她说的"。** | 自己回复自己 | companion-architectures §9 坑 4 |
| R10 | **主人回合漏回复的兜底**〔新提议 N8〕 | 静默空回复 | openclaw-architecture §8.1.1（#116277、#121058）；决策 6 |

**〔新提议 N8〕主人回合漏回复的兜底。** 结构隔离的代价是：模型可能把回答写成原始文本、忘了调 `reply`，主人就收不到。OpenClaw 的 issue 里，deepseek-v4-flash 正好出现过"一轮跑完却没有生成回复"（#116277、#121058）。做法：主人发起的回合结束时没有任何对外动作 → 代码发现 → 追加一轮，提醒"主人在等你回复" → 还是没有 → 本体用她口吻的固定兜底发给主人（例如"我刚走神了，你再说一遍？"），并记一条质量事件，作为决策 6 那 20 个场景评测和备用大脑切换的统计依据。原始文本永远不直接转发。

### 8.3 跨场合发言与受众边界

代码能保证两件事：**谁能对哪里说话**（R2、R4），以及**谁的上下文里有什么**（在场分身的记忆快照、召回、广播都按受众过滤，§11.4）。麦麦的经验也是"隐私边界靠上下文构造，不只靠提示词"（依据：companion-architectures §2.2 Q1 Focus）。

代码保证不了的是：主意识用 `relay` 转话时写的"意图"和"可公开事实"里有没有夹带不该说的内容。主意识能看到全部记忆，这条通道是剩下的唯一缝。本稿的处理是：`relay` 的参数分成"意图"和"可公开事实"两栏，结构上提醒主意识只写可公开的东西；每次转话都留痕，主人可查；不做内容级的自动审查。这是一个需要主人接受的残余风险，见 §17.2 C5。

### 8.4 为什么用结构而不用提示词

- 靠提示词让模型"除最终回复外都输出 NO_REPLY"，在 OpenClaw 里被证明脆弱（依据：openclaw-architecture §8.1.1 #25592）。
- Letta、麦麦、GWA 不约而同地把"对外说话"做成显式动作（依据：companion-architectures §3.2 Q3、§2.2 Q1；papers-architecture §2.2）。
- 显式动作让执行处能做准入、目标检查和写日志，这正是原则 P3。

代价有两个：一是模型可能漏调（R10 兜底）；二是主控台的逐字吐出要看适配器能否流式拿到工具参数（§16 第 4 条）。

## 9. 扩展边界

### 9.1 三类插件

| 类别 | 是什么 | 本体负责 | 插件负责 | 运行位置 | 版本 |
| --- | --- | --- | --- | --- | --- |
| 大脑插件 | CLI 适配器 | 可执行文件解析、环境变量清洗、人设内容、内核工具、准入、写日志 | 传输、会话状态、事件归一、人设映射到原生字段 | 适配器代码在进程内，CLI 是子进程 | V1：Claude、Codex（通用 ACP 见 §17.2 C3） |
| 形态插件 | 渠道适配器 | 认人、场合键、路由、门控、受众、对外发言工具、准入 | 入站归一、出站投递、账号与配对、成员快照、声明平台限制 | 子进程〔新提议 N3〕 | V2 起；主控台和网页是内置形态 |
| 能力插件 | 听、说、看、画、嵌入向量 | 选哪个实现、回退链、花钱预审、取消信号、用量换算 | 调某家服务或本地模型 | 线上实现在进程内；本地实现在进程外〔新提议 N3〕 | V1 后期 |

依据：决策 7；paseo-architecture §2.2 Q7（provider 插件"daemon 负责可执行文件解析和环境变量清洗，插件负责传输和会话状态"）、§3"哪些适合灵鲸的三类插件"；openclaw-architecture §2.2 Q7（渠道插件和核心的分工）。

两条通用规则：

- **插件只能用开发包公开的入口**，不能引用本体内部代码（依据：openclaw-architecture §2.2 Q3、Q7）。
- **版本不叠兼容层。** 每个插件声明自己实现的协议版本；对不上就拒绝加载，并给出明确的错误，不写兼容垫片。OpenClaw 升级后腾讯的微信插件直接报找不到 `openclaw/plugin-sdk` 而加载失败（依据：用户全局原则；openclaw-architecture §8.1.2 #52885；client-backend §3.3）。

### 9.2 大脑插件：统一契约的轮廓

以 Paseo 的 `AgentClient` / `AgentSession` 为起点裁剪（依据：决策 2；paseo-architecture §2.2 Q4、§2.2 Q10 第一行）。

**大脑客户端**（每种 CLI 一个）：

- `describe()` → 能力声明：流式、续接、steer、中断、原生工具、权限钩子、回滚、用量完整度。
- `isAvailable()` → 能不能用、为什么不能用。
- `createSession(配置)` → 大脑会话。
- `resumeSession(续接句柄, 配置)` → 大脑会话。
- 配置包括：人设（稳定段、运行时段）、工作目录、CLI 数据目录、内核工具（端点和会话令牌，或原生工具注入）、原生工具策略、模型、环境变量。

**大脑会话**：

- `startTurn(输入)` → 回合号。
- `steer(输入, 期望回合号)` → 已接受或不支持。
- `interrupt()`：幂等。
- 事件流：回合开始；回合完成（**用量必填**）；回合失败（类别：可重试、鉴权、内容被拒、额度用尽、进程退出）；条目（消息、推理、归一后的工具调用）；权限请求；用量更新。
- `respondToPermission(编号, 允许或拒绝)`。
- `describePersistence()` → 续接句柄，本体当缓存存着。
- `canStopRuntime()` → 现在能不能回收进程。
- `close()`。

相对 Paseo 的改动：

1. 回合完成时**用量必填**，因为花钱总闸要靠它；订阅制 CLI 报不出费用的，报账户额度窗口（依据：paseo-architecture §3"AgentUsage 全是可选字段"一行）。
2. 人设拆成"稳定段"和"运行时段"（依据：paseo-architecture §2.2 Q10 第一行、§3 第二行）。
3. 加上游的 `canStopRuntime`（依据：paseo-architecture §2.2 Q9）。
4. 回合失败带类别，备用大脑切换要用（§12.3）。
5. 裁掉只给界面用的字段（依据：paseo-architecture §2.2 Q10 第一行）。

**人设映射**由适配器负责（依据：决策 4；paseo-architecture §2.2 Q4；early-findings §2）：

| CLI | 注入方式 |
| --- | --- |
| Claude Code | `systemPrompt: {type: "preset", preset: "claude_code", append: 人设}` |
| Codex | `developer_instructions`；会不会被 Codex 原生子 agent 继承要实测（§16 第 3 条） |
| 通用 ACP | 没有对应字段：写进会话工作目录里的指令文件，或作为提示词前缀 |

**适配器必须遵守的三条**：CLI 在两个回合之间退出也要报成回合失败；中断幂等，被拒或超时就失败即关闭；中断时丢掉还没被读走的 steer（依据：paseo-architecture §2.2 Q4、Q5）。

### 9.3 形态插件【V2】

- **感知**：入站事件的结构是"平台、成员账号、场合地址、发送者（平台账号、昵称、群名片）、内容段树（文字、图片、语音、表情、@、回复）、平台消息号、时间"。路由键里一开始就带"哪个账号"，第五版多个成员各用自己的账号时不用改结构（依据：companion-architectures §2.2 Q7 maim_message 的 Seg 树、`RouteKey(platform, account_id, scope)`，§7.2）。
- **行动**：`deliver(场合地址, 内容段, 幂等键)` → 回执（平台消息号）或错误（类别、能否重试）。
- **成员快照**：上报完整快照或有序增量，带代际号和过期时间；状态分当前、过期、不可用（依据：companion-architectures §5.2 Q2，eliza 成员权威）。
- **能力声明**：支持的聊天类型、媒体、表情回应、频率限制和主动发言限制。QQ 官方机器人主动推送已经大幅受限，每群每月主动 4 条，这类限制要由插件声明、由本体遵守（依据：early-findings §1；openclaw-architecture §2.2 Q7 能力声明）。
- **准入策略在本体**：谁能和她说话（只认绑定账号、陌生人私聊怎么处理）由 social 和 gate 统一决定，插件只交原始事件。Letta 的 ChannelGateway 是所有渠道唯一的策略点；OpenClaw 在每次副作用前重新检查发送者的实时权限（依据：companion-architectures §3.2 Q7；openclaw-architecture §2.2 Q7 `assertAuthority`）。
- **插件不得**：判断回不回、调模型、存记忆、订阅全部输出；它只收到发往自己场合的投递（依据：companion-architectures §9 坑 12、坑 14）。

### 9.4 能力插件【V1 后期】

接口轮廓采用 ability-plugins §3.1 的草案，这里只列和整体有关的部分：

- 所有能力共用：调用上下文（调用号、属于哪个成员、**取消信号**）；实现声明（线上或本地、`readiness()`、`estimateUsage()`）；用量报告保留原始计量单位（字符、秒、token、张），换算成钱只在 guard 里做（依据：ability-plugins §3.1、§4 第 11 条）。
- 取消信号和一键暂停、花钱总闸共用同一个，取消必须真正停止计费，例如关掉 WebSocket（依据：ability-plugins §3.1、§3.3）。
- 说：`bindVoice`（复刻会过期，原始录音由本体保存）和 `openSynthesis`（会话式、分块输出、每块对应文字区间）。第一版的语音消息也走会话式接口，第五版实时通话直接复用（依据：ability-plugins §3.1、§3.3、§4 第 1 条）。
- 听：转写结果每段带情绪和声音事件。看：可以带问题"再看一眼"同一张图。画【V2】。嵌入向量：给记忆召回和群聊第二道门用（见 §17.2 C2）。
- 回退规则：每种能力一条有序的实现链，只有可重试的失败（网络、限流、5xx、超时）才换下一家；一条语音中途不换家，因为换家等于换声音（依据：ability-plugins §3.1"回退规则"）。

### 9.5 内核工具目录

见 §5.10。工具目录和传输无关：CLI 支持原生工具就直接注入，否则经 MCP 端点；每个会话一个令牌，按会话种类、自主开关、被收回的能力过滤（依据：paseo-architecture §2.2 Q7、§5 坑 8）。

### 9.6 技能与自写工具【V4】

她自己写的工具是不可信代码，走单独的隔离通道，不进"完全信任"的插件通道；只有在活经过验证之后才成为技能候选；带版本、可回滚；不做市场（依据：papers-architecture §5.3；openclaw-architecture §5 坑 12；paseo-architecture §5 坑 13）。细节留给成长模块。

## 10. 多端连接与同步

以 client-backend 的结论为准，这里只列整体架构层面的决定。

### 10.1 协议

- 三种信封：请求、响应、事件；连接建立时先握手（客户端报协议版本、构建号、客户端种类和各订阅的游标，服务端回能力和限制）；方法名用点分命名（依据：client-backend §3.3）。
- 有副作用的请求一律带幂等键（依据：client-backend §3.3；openclaw-architecture §2.2 Q1）。
- 前端由本体托管、同版本发布；协议版本或构建号不一致时，客户端提示刷新，不做兼容。仍守三条规则：schema 只增不删、纯结构、用可辨识联合类型，给第五版的手机端留余地（依据：client-backend §2、§3.3）。

### 10.2 订阅与同步

| 事件类别 | 内容 | 同步方式 |
| --- | --- | --- |
| 实体 | 看板卡片、成员状态、会话列表等的增改删，带实体版本 | 游标过期就给快照 |
| 时间线 | 已提交的条目，按（会话，序号）分页 | 打开会话只取最新尾页 |
| 实时流 | 逐字吐出的增量，按偏移去重 | 不重放，丢了就等条目提交 |
| 注意力 | 审设计、验收、出错、她想你了 | 见 §10.4 |
| 系统 | 健康、暂停、花费、总闸 | 实体方式 |

术语：**游标**是客户端上次读到哪；**快照**是某个时刻的完整当前状态；**背压**指客户端跟不上时，服务端降级推送而不是在内存里越堆越多。

- 只给正在看的会话推逐字增量，其他活只推看板变化；每个会话 60–100 毫秒合一帧，第一帧立刻发（依据：client-backend §2、§3.4）。
- 每个连接有发送缓冲上限，超了就降级为只推条目完成；单帧不超过 256 KB；工具输出截断，全文按需取；diff 先发文件清单和统计，具体改动按需取（依据：client-backend §2、§3.4）。
- 图片、语音、文件走 HTTP，支持断点续传和缓存，不塞进 WebSocket；远程连接开压缩；客户端在浏览器本地缓存已提交的条目，先画缓存再对账（依据：client-backend §3.4）。这几条是为了 Tailscale 走中继时不到 70 KB/s 的实际带宽（依据：early-findings §4）。

### 10.3 多个客户端同时在线

主人的主控台和网页是同一个场合（§2.2），所以同时开着的几个客户端看到的是同一条主意识时间线；从哪个客户端发的消息都进主意识，回复出现在所有客户端上（依据：companion-architectures §2.2 Q3）。客户端在线状态（哪些开着、最近一次活动）是进程内信号，给 notify 和 `sayToOwner` 选场合用，不进日志。

### 10.4 通知路由

- 有客户端正在看相关内容 → 什么都不推；最近有活动的客户端 → 应用内提醒；都不在线 → 系统通知；第二版起可以经 QQ、微信发到手机（依据：paseo-architecture §2.2 Q8 `computeNotificationPlan`；product.md「形态」"通知"）。
- 网页的系统通知要求安全上下文：本机 `localhost` 可以，远程要经 Tailscale Serve 提供 HTTPS；标签页关了就收不到。这是第一版要不要先做 Electron 薄壳的主要考虑（依据：client-backend §3.7；见 §17.3 P3）。

### 10.5 前端结构

包划分（协议、客户端连接、本体、界面、以后的桌面壳）、状态的四类划分、`HostBridge` 接口（网页和 Electron 两种实现）、主控台的信息架构，照 client-backend §3.5、§3.6，细节留给客户端界面和前后端两个模块。

## 11. 安全与权限

### 11.1 信任边界

- **一个本体就是一个主人的信任边界。** 不支持互不信任的人共用一个带工具的 agent（依据：openclaw-architecture §2.2 Q8）。
- **非主人发起的回合，不带主人的权限。** OpenClaw 的模型是"所有能给 agent 发消息的人共享它的工具权限"，灵鲸的外部群正是互不信任的多方场景，所以在场分身只有最小工具集，没有 CLI 原生工具（依据：openclaw-architecture §2.2 Q8、§3"一个 Gateway 一个信任边界"一行；§5.10）。
- **处置顺序：先身份，再范围，最后才指望模型**（依据：openclaw-architecture §2.2 Q8）。
- **网络暴露**：默认只绑本机回环地址；每个请求校验 Host 头白名单，防 DNS 重绑定攻击；远程只经 Tailscale Serve 的 HTTPS 加令牌；本机的命令行和桌面端用每次启动重写、权限 0600 的本机凭据文件（依据：paseo-architecture §2.2 Q8）。OpenClaw 公网暴露的实例据报超过 13 万，原因被归到默认绑所有网卡（依据：openclaw-architecture §2.2 Q10 用户痛点第 2 条）。
- **同一系统用户下的进程挡不住**：Paseo 明说密码挡的是网络客户端和其他系统用户，挡不住以同一身份运行的进程（依据：paseo-architecture §2.2 Q8）。CLI 子进程正是同一身份，所以要靠 CLI 自己的沙箱拒绝它们读本体的数据目录和凭据文件，见 §11.9 的〔新提议 N9〕。

### 11.2 身份绑定

- 真人只按主人绑定的身份声明认。形态插件上报的昵称、群名片只是证据（"观察到"），永远不能授权私密内容跨场合披露；同名推断出的关联也不能（依据：companion-architectures §5.2 Q2、§7.2、§9 坑 15）。
- 合并、拆分是带版本的重定向，可以回退，方便主人更正（依据：companion-architectures §5.2 Q2）。
- 嘴上说"我是她妈"不改变身份；角色只有主人能改（依据：product.md「规矩」"身份只认绑定"）。
- 主人的身份 = 主人绑定的账号 + 本机主控台登录。

### 11.3 每个会话一个令牌

- 每个会话创建时拿到自己的令牌（一串随机字符，持有它就证明"我是谁"），toolport 从令牌推出调用方是哪个成员、哪种会话、绑在哪个场合或任务上；会话关闭或换新时令牌作废（依据：paseo-architecture §3"MCP 调用方身份"一行）。
- 反例是 Paseo：所有 agent 共用一个令牌，身份放在 URL 参数里，任何 agent 都能冒充别的 agent（依据：paseo-architecture §2.2 Q8、§5 坑 8）。
- 朋友的会话【V3】拿的是朋友的令牌，没法以她的名义做事。

### 11.4 按受众的隐私

| 规则 | 做法 | 依据 |
| --- | --- | --- |
| 默认最严 | 每条事件、每条记忆带来源和受众；没有明确受众的按"只有主人" | companion-architectures §5.2 Q2（eliza v2"owner-private is the fail-closed default"） |
| 受众取最小 | 场合里只要有一个人不该知道就不说；成员快照过期或不确定时按最严 | companion-architectures §5.2 Q2、§7.2 |
| 上下文就是边界 | 在场分身的创建快照、每轮召回、广播提醒都按受众过滤；它的上下文里根本没有不该说的东西 | companion-architectures §2.2 Q1（麦麦"隐私边界靠上下文构造"） |
| 跨场合在目标处生成 | §8.2 R3 | companion-architectures §7.1 |
| CLI 那一侧也算 | §6.4、§6.7 | openclaw-architecture §5 坑 10 |
| 第一版就写来源 | 第一版只有主人一个受众，但来源字段从第一版就写全，第二版不用迁移数据 | client-backend §3.2 |

主人能查看全部记忆（依据：product.md「记忆」）。至于她和主人聊天时，会不会主动说出家人私下告诉她的事，是一个产品问题，见 §17.2 C6。

### 11.5 防操控

- **外部内容打标。** 外部内容用"不可信"标记包起来，并去掉各家聊天模板的特殊 token（依据：openclaw-architecture §2.2 Q8）。
- **伪造的结构块被转义**（§8.2 R5）。
- **别人的话改不了她。** 出生设定只有主人能改；成长要多个来源的重复证据并按来源加权；非主人说的关于主人的事，记成"某某说的"，不记成事实（依据：openclaw-architecture §2.2 Q6；papers-architecture §6 I"非主人来源的内容不能直接改成长"）。
- **长对话漂移。** 对话越长，越会采纳对方的指令；在场分身按轮数换新，人设在稳定段里（依据：papers-architecture §2.8、§6 I）。
- **只有发起者能 steer**（§4.7）。
- **在场分身可以报告。** 用 `flag` 报告可疑的操控，生成通知给主意识；主人可以屏蔽某个账号（依据：product.md「规矩」"防操控"）。
- **防记忆投毒。** 写进记忆之前清洗（§6.6）；读过网络内容的回合打污染标记（依据：openclaw-architecture §2.2 Q6；papers-architecture §2.3 记忆攻击）。

### 11.6 主人专属的控制项

创建成员、改出生设定、拨自主开关、配大脑、绑定身份和改角色、改主人设定的关系、设预算和总闸、一键暂停、收回能力、查看更正删除抹掉记忆、回滚成长、审核任务、管理形态账号。这些**只经 gateway 的主人接口**，不做成内核工具，任何会话都调不到（依据：product.md「灵鲸里有谁」「规矩」）。反例是 OpenClaw：agent 能自己改写 SOUL.md，文档里没看到硬限制（依据：openclaw-architecture §2.2 Q4）。

### 11.7 一键暂停【V1】

1. 主人在主控台按暂停，或从主人账号发 `/暂停`（不经模型）（依据：companion-architectures §3.2 Q3）。
2. guard 进入暂停：不再放行新回合和新动作；当前的取消信号触发，正在进行的能力调用中止、语音合成的连接关掉。
3. conversations 中断所有正在跑的回合。中断是幂等的；**每个会话都确认停下才算暂停完成**，确认不了的就失败即关闭，必要时杀进程（依据：paseo-architecture §3"中断幂等"一行、§2.2 Q4）。
4. scheduler 停止触发作业；恢复时按补跑策略处理错过的。
5. 感知不停：消息照样写进日志，不丢，但她不回。恢复后，主意识收到一条由代码生成的"暂停期间发生了什么"的汇总通知，不把消息一条条重放。
6. 主控台在暂停期间照常可以查看和修改。
7. 也可以只暂停一个会话、一个成员或一个形态。

### 11.8 花钱总闸【V1】

- **一个闸，在 guard 里，她不知道**（依据：决策 9）。
- **拦截点**：每个回合开始前（按会话种类的历史平均值预估）；每次能力调用前（能力插件的 `estimateUsage`）；长时间干活的回合中途定期检查；每个回合、每次调用结束后按实际用量记账（依据：paseo-architecture §3"总闸放在 startTurn 之前"；ability-plugins §3.1）。
- **计量**：保留原始单位，换算成钱只在 guard 里做；订阅制 CLI 报不出费用的，用账户额度窗口（依据：paseo-architecture §3；ability-plugins §4 第 11 条；§16 第 6 条）。
- **〔新提议 N10〕分三档**：
  - **正常**；
  - **节省**（过了主人设的软线）：停掉自主触发、白天的增量整理和主动关心；主人的消息、主人派的活、在场分身被点名照常；
  - **停止**（到了硬线）：不再起新回合和收费调用，正在跑的回合在下一个安全点停；主人在主控台看到状态和"提额"入口；对外场合静默；她不被告知原因。
  - 这和决策 9"预算不是叫醒伙伴的条件"不冲突：总闸对所有活动一视同仁，不是某次叫醒的前提。
- OpenClaw 至今没有网关层的花费上限，请求它的 issue（#42475）从 2026 年 3 月开着，说明这是要从一开始就自建的东西（依据：openclaw-architecture §8.1.1）。

### 11.9 能力收回、可写边界与不可逆动作

- **按类别收回能力**：对外场合发言、主动找人、shell、写文件、联网、收费能力（如语音）、叫朋友、自写工具【V4】。内核工具在 toolport 过滤；CLI 原生工具靠权限策略和沙箱配置；能力插件在调用前检查（依据：product.md「规矩」；paseo-architecture §3"工具目录"一行）。
- **〔新提议 N9〕CLI 的沙箱边界 = 快照边界。** 干活分身的 CLI 用它自己的沙箱（Codex 的沙箱模式、Claude Code 的权限规则）把可写范围限制在本任务的 worktree 里，同时拒绝读本体的数据目录和凭据文件。这样它能改动的一切都在快照覆盖之内，"兜底靠可撤销"在结构上成立；越出边界的操作作为权限请求交给主人。理由：shell 里的 `rm` 本体拦不住，只有把可写范围收进快照范围才能保证可撤销；OpenClaw 的工作区不是沙箱，用绝对路径照样能碰到主机上任何地方；同一用户身份的进程能读到本机凭据（依据：product.md「规矩」"改文件前先打快照，删除只进回收站"；openclaw-architecture §5 坑 5；paseo-architecture §2.2 Q8；client-backend §3.1 workspace）。两家 CLI 的沙箱能否做到"写只限 worktree、读不到指定目录"要实测（§16 第 7 条）。
- **〔新提议 N11〕不可逆的外部动作单列清单。** "兜底靠可撤销，不靠审批"只覆盖可撤销的动作。付款、删除远端数据、公开发帖或评论【V4】这类撤不回的外部动作，默认关闭，或每次要主人确认；在她被允许的场合里聊天不算在内。依据：papers-architecture §6 I 指出需要例外清单；AIOS 的访问管理器对不可逆操作强制用户确认（依据：papers-architecture §2.4）。它和"完全自主，事前不审批"可能冲突，见 §17.1。

## 12. 出错与恢复

### 12.1 本体重启

launchd 拉起后按顺序：

1. **自检**：SQLite 版本、NUL 往返、磁盘余量（§6.8）。
2. **日志恢复**：有开始没结束的回合补记"被打断"；有"将要做"没结果的补记"结果不明"（§6.5）。
3. **清孤儿进程**（§3.4）。
4. **投影追上**：异步投影从各自的检查点继续。
5. **作业**：重建定时器；错过的按补跑策略，承诺类补，巡检类不补（依据：paseo-architecture §5 坑 5；openclaw-architecture §2.2 Q5）。
6. **通知**：没消费的通知还在收件箱；主人没确认的注意力事件重新推送。
7. **会话**：按需续接（依据：paseo-architecture §2.2 Q5）；残留为"运行中"的会话修成"已关闭"或"出错"（依据：paseo-architecture §2.2 Q5，上游 0.13 的修复）；主人发起的被打断回合按 §6.5 续跑。
8. **告诉她离开了多久**：在下一次主意识回合里提一句"你离线了 X 小时"（依据：companion-architectures §2.2 Q1、§7.3）。

连续启动失败达到次数预算时，不再续跑被打断的回合，只起主控台，等主人处理（依据：openclaw-architecture §7 J"3 次启动失败用尽预算"）。

### 12.2 CLI 崩溃与卡死

- 回合中途崩溃：适配器报回合失败。两个回合之间崩溃：适配器同样报失败，会话进入出错状态（依据：paseo-architecture §2.2 Q5、§5 坑 9）。
- 回合卡住：看门狗中断（§3.4）。
- 下一次有输入时用续接句柄续接；续接失败就用同一个大脑开新会话，从日志重建（§3.4）。
- CLI 里挂着的后台 shell 会随进程一起丢，这件事要写进日志和任务记录，不能假装还在跑（依据：paseo-architecture §2.2 Q5）。
- 同一个会话反复崩溃：干活分身的任务标成失败并通知主人；主意识走 §12.3 的备用大脑。

### 12.3 模型接口失败与备用大脑

- CLI 自己会重试，本体看到的是带类别的回合失败（依据：paseo-architecture §2.2 Q5）。
- **切换条件**（可配置）：可重试的失败连续 N 次、续接失败、额度用尽、鉴权失败。
- **切换方式**：用备用大脑开新会话，上下文从日志重建：人设、当下状态、交接摘要、召回记忆、最后 N 轮原文。不能靠旧 CLI 的转录，因为换了大脑就是换了 CLI（依据：paseo-architecture §3"交互式 agent 不切换备用大脑"一行；决策 6）。
- **重发规则**：失败的那一轮如果还没产生任何副作用，就把输入原样重发；已经产生了，就发续跑提示，写明哪些已做、哪些结果不明（依据：companion-architectures §4.2 Q3 AIRI"有输出或工具调用之后不再重试"、§7.6）。
- **出错也像人**：主人的场合里说一次"我脑子有点懵，等我缓缓"；对外场合沉默（§8.2 R8）。
- 每次切换都是一条日志事件和一条系统通知，主人看得到。什么时候切回主大脑留给 CLI 编排模块。
- **后台任务**用"一次性内部会话 + JSON Schema 校验 + 重试 + 按大脑列表逐个兜底"，照搬 Paseo 的 agent-response-loop（依据：paseo-architecture §2.2 Q10、§3）。

### 12.4 通知至少送达一次

- 通知由日志事件生成，本身持久；进了某个回合、而且那个回合成功结束，才标记已消费；否则下次重新投递。投递时带通知编号，重复的在前缀里合并（依据：paseo-architecture §2.2 Q9 完成订阅："先写意图再承诺通知；至少一次投递"）。
- 给主人的注意力事件有"主人已看到"的确认，没确认就按规则重推，设备侧去重。
- 反例：OpenClaw #44925，子 agent 完成后回报失败，结果静默丢失，超时后既不重试也不通知（依据：openclaw-architecture §8.1.1）。

### 12.5 对"完成"的核验

- 干活分身说"设计已交"，tasks 核对设计文档在不在；说"做完了"，核对文件有没有 diff、声称跑过的测试有没有执行记录、声称的产物在不在（§4.6）。
- 核对不了的说法在交给主人的报告里标出来。
- 主人验收是最后一层核验（依据：papers-architecture §6 J"验收算一层验证"、§2.5 MAST；openclaw-architecture §8.1.3 第 3 条）。

### 12.6 循环与坏输出

- 每个回合有工具调用次数和步数上限；连续"等待"有上限；同一工具用同样参数反复调用就中断（依据：companion-architectures §2.2 Q4、§9 坑 3（麦麦 #1710：弱模型不会正确结束，循环跑满）；papers-architecture §2.5（MAST 步骤重复占 15.7%；E3 要有停止条件））。
- 陷入过循环的会话片段，清洗之前不能作为记忆来源，防止在 agent 之间传染（依据：openclaw-architecture §8.1.2 #113346）。

### 12.7 形态适配器故障【V2】

- 子进程崩溃：formhost 在次数预算内重启；超出就熔断，这个形态标成离线，并通知主人（依据：companion-architectures §2.2 Q7（麦麦插件 Runner 的健康检查、最大重启次数、熔断））。
- 断线期间的消息：平台支持拉历史的，重连后补拉，作为"迟到的消息"写进日志；只有近期点了她名的才唤醒（依据：openclaw-architecture §2.2 Q7 持久入站与重放去重）。
- 出站失败：可重试的用同一个幂等键重试；不可重试的记失败，生成系统通知。

### 12.8 升级与迁移〔新提议 N12〕

1. **先备份**：node:sqlite 的 `backup()`。
2. **排空**：不再放行新回合，等正在跑的回合结束（超时就中断并留续跑提示），再重启。这是 rainbow deployment（新旧版本并行、流量逐步切换）在单机上的简化（依据：papers-architecture §2.5 E1、§6 J）。
3. **迁移是一次性的**：投影的变化靠从日志重建；日志事件格式的变化走"备份 → 写出新库 → 校验（事件数、投影校验和）→ 切换"，旧库留作备份。不在代码里保留按版本分支的兼容逻辑（依据：用户全局原则"改在根上、不叠兼容层"；client-backend §2 Paseo 的 `COMPAT` 垫片、§4 坑 1）。
4. **接收方确认写入之前不删旧数据**：OpenClaw 的 `doctor --fix` 在没有接收方的时候删了 `HEARTBEAT.md` 还报迁移成功（#123057）；旧路径也删得比升级窗口早（#113131）（依据：openclaw-architecture §8.1.2、§8.2）。
5. 插件协议版本对不上就拒绝加载（§9.1）。
6. 升级可以回退：恢复备份 + 上一个构建。

## 13. 成本控制

总原则：**成本取决于起了多少个模型回合，不取决于单个回合写得多巧**（依据：papers-architecture §5.2 第 5 条、§8.1 第 8 条）。所以闸门都设在"起不起回合"上。

| 烧钱的地方 | 为什么会烧 | 闸门 | 依据 |
| --- | --- | --- | --- |
| 主意识回合 | 主人每条消息、每批通知、每次自主触发都起回合；上下文越长单价越高 | 连发合并；通知 2 秒合并加配额；自主触发过三道闸；人设放缓存边界上方，易变内容放下方；按上下文压力和作息换新；每回合步数上限 | 决策 13；openclaw-architecture §8.1.2（#61690：空的 HEARTBEAT.md 每 30 分钟重放整段历史，每次约 2.7 万输入 token；#20894：每条消息的元数据注入系统提示，cache_write 增加 80–170 倍） |
| 在场分身【V2】 | 群消息多 | 两段门控（不调模型）、防抖、空闲退避、闲置回收、按轮换新 | 决策 13⑥；companion-architectures §2.2 Q4（麦麦 #1710：只说了十句话，半天吃掉 1000 万输出 token） |
| 干活分身 | CLI 工具循环长 | 交接包里的花费上限、看门狗、步数上限、总闸 | paseo-architecture §3；papers-architecture §2.5 E1（多 agent 约 15 倍 token） |
| 后台整理 | 抽取、巩固、日记 | 按批不按条；检查点只处理增量；只在空闲和夜里；同一时刻只跑一个 | companion-architectures §2.2 Q4（麦麦 #352：话题总结每小时约 20 万 token 且重复处理）、§7.4 |
| 请教强大脑 | 强模型单价高 | 只在代码规定的类别调用，每天有次数上限 | papers-architecture §2.6（Advisor 用 `max_uses` 限次数）、§3.4 |
| 能力调用【V1 后期】 | 合成、识别、看图按量计费 | 调用前预审；缓存（语音按"文本 + 情绪 + 音色 + 模型"哈希，图片按 sha256 和感知哈希）；取消即停止计费 | ability-plugins §3.1 |
| 闲置的 CLI 进程 | 不花钱但占内存 | 闲置回收 | paseo-architecture §2.2 Q9 |

另外三条：

- **保护前缀缓存。** 稳定人设块里不放消息号、时间戳；当下状态、提醒都放在每轮前缀；成长版本只在换新会话时变。OpenClaw #143017 记录了持久会话五种改写前缀的方式，实测 2130 万 cache-write token（依据：openclaw-architecture §8.1.2、§8.1.3"和已定决策直接相关的另外两点"）。
- **兜底是唯一的总闸**（§11.8）。
- **看得见。** 主控台的"日志与花费"按天、按任务、按大脑统计，总闸在那里设置（依据：product.md「主控台」；client-backend §3.6）。

### 15.2 骨架包含什么

handoff 定了"第一版拆成若干里程碑，骨架先行"。这里只列骨架包含什么和建议的生长顺序，不是实现计划。

**骨架**是一条从主控台进、经 CLI、再回到主控台的最细链路，每一层都有一个真实但最小的实现：

1. 基础：journal（追加、读取、订阅、内联投影、启动自检、备份）。
2. 守护：guard（暂停、用量记账；总闸先只有硬线）。
3. 资源：procs（登记、拉起、清孤儿）+ brains 的 Claude 适配器（Claude Code + DeepSeek Flash，人设追加注入）。
4. 运行：conversations（主意识会话、邮箱、回合生命周期）+ context（人设层和本轮输入）+ actions（先记后做）。
5. 编排与接入：gate（主人路由）+ outbox（`reply`）+ toolport（会话令牌、`reply` 工具）+ gateway（握手、发消息、订阅时间线）+ 只有对话框的主控台。

骨架完成的标准是跑通 §4.3"链路一：主人私聊"，包括重启后续接、结果不明的标记、一键暂停。

**之后的生长顺序建议：**

6. mind（通知、收件箱）+ tasks + Codex 适配器 + workspace（worktree、快照）→ 跑通 §4.6"链路四"。
7. scheduler + agenda（`commit`）→ 跑通 §4.5"链路三"。到这一步就可以做决策 6 要求的约 20 个真实场景评测。
8. persona 和 memory 的投影 + 内省会话 + 夜间作业链 + 换新会话。
9. abilities（语音、看图）。

这样排的理由：最先验证风险最大的假设，也就是"CLI 当主意识大脑"（决策 6）、"回复是工具调用"（§8、§16 第 4 条）、日志与恢复语义（§6.5）。如果其中哪条不成立，越早发现，改动越小。

## 17. 需要用户确认

### 17.1 本稿的新提议

每条给出推荐和理由。都没有直接的调研依据，是从依据推出来的。

**N1 内省会话作为第四种会话**（§2.1）
- 提议：后台整理记忆、写日记、提成长的会话单列一种，执行者是她，带她的人设，不对外，只交结构化产出，用完即弃。
- 推荐：采纳。决策 4 让后台任务走 CLI，决策 5 规定没有无人设的 agent，两条合起来执行者只能是她；它不面向任何人，所以不属于决策 12 的三种会话，是补充而不是推翻。
- 备选：把后台任务算成干活分身的一种。缺点是干活分身有任务流程和审核点，后台任务不需要；看板上会冒出大量内部条目（Paseo 用 `internal` 标记专门把这类对话藏起来，见 paseo-architecture §3）。

**N2 自主开关关闭的成员，主人直接找它时按需开会话**【V3】（§2.2）
- 推荐：采纳，第三版再细化。结构和主意识会话一样，只是没有自主触发、关注清单和作业，闲置回收。
- 备选：主人只能通过她去找伙伴。和 product.md「谁能叫醒开关关闭的伙伴」冲突。

**N3 外部平台的形态适配器、本地能力模型放进程外**（§3.5）
- 推荐：采纳。OpenClaw 的单进程里一个外部依赖就能拖垮全局；放进程外后，崩溃和内存泄漏只让那一个形态或那一项能力离线。
- 代价：多一层 IPC 和子进程管理。
- 备选：全部进程内，简单但不隔离故障。

**N4 内核工具在调用当中同步执行**（§4.1）
- 推荐：采纳。执行权、准入、写日志仍在本体；CLI 能拿到结果接着做；不依赖"模型能正确处理'已受理未执行'"这个没验证过的前提。
- 备选：麦麦式"只记录决策、回合结束后再执行"。

**N5 主人的消息抢占非主人发起的回合**（§4.7）
- 推荐：采纳。没产生副作用的通知或自主回合在安全点中断，通知放回收件箱，先回主人；已产生副作用的跑完再回主人。
- 备选：一律 steer（有 OpenClaw #30197 那种吞掉回复的风险）；一律排队（主人要等后台回合跑完）。

**N6 异步投影单独放一个可重建的库文件**（§6.3）
- 推荐：采纳。重建和索引膨胀碰不到装真相的文件，备份也更小。
- 备选：一个库，简单，但索引和投影的问题会影响真相文件（OpenClaw #143524）。

**N7 日志脱敏：唯一允许的日志改写**（§6.7）
- 推荐：采纳，并在第一版就做，因为第一版包含"主人可以删除任何一条记忆"。只有主人能发起，本身留痕。
- 可能冲突：和"日志只追加"冲突，这是有意设的唯一例外。
- 备选：只做"隐藏式删除"，原文仍在日志里，"删除"名不副实。

**N8 主人回合漏回复的兜底**（§8.2 R10）
- 推荐：采纳。代码发现主人回合没有对外动作 → 追加一轮提醒 → 仍没有就发她口吻的固定兜底，并记质量事件。
- 备选：把原始文本直接发给主人。这会破坏结构隔离，内部内容会漏出来（OpenClaw #143278 一类问题）。

**N9 CLI 的沙箱边界 = 快照边界**（§11.9）
- 推荐：采纳，以 §16 第 7 条实测通过为前提。干活分身只能写本任务的 worktree，读不到本体数据目录和凭据；越界的操作交主人。
- 备选：只靠事后快照、不限制可写范围。worktree 以外的改动撤不回，"兜底靠可撤销"在那部分不成立。

**N10 花钱总闸分三档**（§11.8）
- 推荐：采纳"正常、节省、停止"三档。需要你定：软线、硬线的数值，以及停止时主控台显示什么。
- 备选：只有一条硬线，简单，但到线时所有活动一起骤停，包括主人正在聊的天。

**N11 不可逆外部动作单列清单**（§11.9）
- 推荐：采纳，清单内的动作默认关闭或每次要主人确认。建议的初始清单：付款或下单、删除远端数据、公开发帖或评论【V4】、主动私聊没绑定过的人。
- 可能冲突：product.md「规矩」写的是"完全自主，事后可查""兜底靠可撤销，不靠审批"。理由是撤不回的动作没法靠撤销兜底，这正是那条规矩没覆盖到的部分（依据：papers-architecture §6 I）。
- 备选：不设清单，全靠事后可查。

**N12 升级先排空，迁移一次性完成**（§12.8）
- 推荐：采纳。先备份，等正在跑的回合结束再重启；日志格式变化走"写出新库、校验、切换"，代码里不留按版本分支的兼容逻辑。
- 备选：在读日志时按版本即时转换旧事件。这是一层长期存在的兼容代码，违背"改在根上、不叠兼容层"。

### 17.2 和已定决策相关、需要确认或补充的地方

**C1 决策 6：主意识的大脑**
- 不推翻决策 6，只补两样东西，供 20 个场景的评测一起比较：
  1. **代码强制升级的类别**：派活、建承诺、跨场合发言、主人情绪低落、拒绝或违背主人。这些情况由代码决定要不要请教强大脑，不让弱模型自己判断。
  2. **可选的 `consult` 工具**：把主意识的完整上下文分叉给一个一次性的强大脑会话，只回计划、纠正或"停"，不调工具、不对外。这个会话同样是带她人设的分身，不违反决策 5。
- 依据：papers-architecture §3.4、§3.5 修正 F；§2.5 E5（"质量上限由主控决定"）；§2.6 Advisor 策略。
- 推荐：骨架里留好这个开关、默认关闭；评测时加"Flash + 请教"一组，按结果定。

**C2 决策 4 与嵌入向量**
- 记忆召回和决策 13⑥ 群聊第二道门都要用嵌入向量。嵌入模型不思考、不行动，不是"大脑"，本稿把它归为能力插件。第一版按决策 8 用线上嵌入服务，以后可换本地（依据：companion-architectures §5.2 Q10"嵌入本来就不是大脑"）。
- 请确认这个归类不违反"大脑全部走 CLI"。

**C3 决策 1、2：第一版要几个大脑适配器**
- 第一版的产品范围是"调度 Claude Code、Codex"，主意识用的也是 Claude Code 外壳，所以第一版只需要 Claude 和 Codex 两个适配器。
- 推荐：通用 ACP 适配器按决策 1 从上游摘进来，但不列入第一版的验收，第一次真正要用时再完善。

**C4 决策 11 与"主人直连分身"**
- 本稿规定：直接打开某个会话只在主控台做；主人从 QQ 等形态说的话一律进主意识，由主意识把原话转过去（§5.8）。
- 理由：外部形态上没有"选择哪个会话"的界面；混进去会让投递目标变得依赖会话状态（§8.1 痛点 2）。
- 请确认。

**C5 决策 12：转话通道的残余风险**【V2】
- 在场分身的上下文按受众过滤，但主意识能看到全部记忆。主意识用 `relay` 转话时写的内容有没有夹带私密信息，代码保证不了（§8.3）。
- 推荐：第二版先接受这个残余风险：参数分"意图"和"可公开事实"两栏，每次转话留痕可查；出了问题再加一个独立会话做检查（代价是每次转话多一个回合）。

**C6 主人能看到全部，她会不会主动说**
- 主人能查看任何一条记忆（product.md「记忆」）。但家人私下告诉她的事，她和主人聊天时会不会主动说出来，是一个产品问题，影响记忆模块的召回规则。
- 推荐：记忆带来源；默认不主动转述别人私下告诉她的事，主人问起时说明来源。请你定。

### 17.3 handoff 里原有的待定事项

**P1 听语音时用本地 SenseVoice 补笑、哭等声音事件**
- 推荐：同意。架构上它只是"听"能力的一个本地实现，放在子进程里（N3）；它出问题只影响声音事件，不影响转写（依据：ability-plugins §3.4）。这是"第一版全线上"（决策 8）的唯一例外。
