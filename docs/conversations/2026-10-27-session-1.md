## 来历

有人把 DeepSeek 的蓝鲸 Logo 丢给模型识别，模型没认出自己，描述成"一条蓝色大肥鱼"。社区随后把它二创成"鲸鱼娘"形象。它不是 DeepSeek 官方角色，只是社区形象。

## 技术实现

### 路线 A：NapCat + OneBot 11 + 应用端（最常见）
- **NapCat** 负责登录一个 QQ 小号，用 OneBot v11 协议收发消息，相当于"收发室"。
- 应用端是"大脑"，可以用 **AstrBot**，也可以自己写 Python。人设、模型、插件都放这里，换协议端也不影响。
- 模型主要用 DeepSeek 的 `deepseek-flash`，语音等扩展能力用阿里云百炼。
- 缺点是用个人号协议，有封号风险。教程建议用注册一段时间的小号、固定 IP、控制发言频率。

### 路线 B：QQ 开放平台官方机器人
- 申请 appID 和 secret，通过 WebSocket 接入，不用逆向协议，所以稳定合规。
- 群聊里只能收到 @ 它的消息，这是它的限制。

### 路线 C：DeepSeek Harness（DSH）
- DSH 是官方的 Agent 运行环境，通过 `@tencent-connect/dsh-qqbot` 扫码绑定 QQ。
- 每个私聊用户和每个群各有独立会话，人设可以用 `dsh-persona-dafeiyu` 这类插件直接装。

## 路线 A 怎么玩

QQ 小号扮演"真人账号"，NapCat 在中间转发消息，AstrBot 是大脑：

```
QQ 小号 ⇄ NapCat（OneBot v11 协议端）⇄ AstrBot（人格 / 记忆 / 插件 / 定时任务）⇄ DeepSeek、阿里云百炼等模型
```

[whyever77/dafeiyu-astrbot](https://github.com/whyever77/dafeiyu-astrbot) 给的上手顺序是：

1. 搭 AstrBot、NapCat，注册一个 QQ 小号并扫码登录。
2. 把核心插件 `astrbot_plugin_face_convert` 放进 AstrBot 的 `data/plugins/`。
3. 在 AstrBot 里新建人格，把 `persona/大肥鱼-人格.md` 整段粘贴进去。
4. 想要语音、记忆、自定义音色，再按导入指南逐项配置。
5. 想 7×24 在线，用仓库里的 Docker Compose 挂到云服务器。

"会看会听会说会记"都是现成组件拼出来的：

| 能力 | 实现 |
|---|---|
| 看图 / 视频 | qwen3-vl 转述，视频先用 ffmpeg 抽帧（默认前 5 分钟，最多 16 帧） |
| 听语音 | NapCat 转 mp3，再用 qwen3-asr-flash 转文字 |
| 说话 | 百炼音色复刻加 qwen-audio-3.1-tts-flash，发语音条 |
| 表情 | 自研插件把 `[旺柴]` 这类文本换成真正的 QQ 表情段。QQ 不会渲染机器人发的纯文本表情码，所以必须这么做 |
| 长期记忆 | livingmemory 插件加 bge-m3 嵌入，每个私聊、每个群各存一份，互不串 |
| 认人 | 插件给群消息注入 `[昵称(QQ号)]` 标记，只进模型上下文，对方看不到 |
| 主动找你 | proactive_chat 插件（随机或沉默触发），加 AstrBot 内置的"未来任务"定时催睡、叫起床 |
| 逛 B 站、点手机 | PhoneMCP 加 ADB 控制安卓模拟器 |

这套的特点是"拼装"：插件多、可调的地方多，但每个组件的版本都要对得上。FigaroGao 的扩展仓库注明参考版本是 AstrBot 4.29.1 加 NapCat 4.18.38，他还用 ARM64 安卓平板加 Termux 当主机，并为 QQ 掉线专门写了恢复器和看守进程。

你这个思路很对：内核不自己写 agent 循环，而是像 Paseo 一样调度现成的 CLI（Claude Code、Codex、Gemini CLI、DSH……）。这样问题就变成"灵魂怎么挂到别人的 CLI 上"。

## 核心原则：灵魂归内核，CLI 只是可替换的手

人格、记忆、认人都由内核持有，CLI 只负责思考和干活。这样今天用 Claude Code、明天换 Codex，它还是同一只大肥鱼，记得同样的事、认得同样的人。

```
  电脑端    QQ    微信    ...        ← 渠道适配器
        └──────┬──────┘
           统一消息
               ▼
  ┌──────────── 内核 ────────────┐
  │ 会话路由  认人  人格  记忆  主动调度 │
  └──────┬─────────────▲────────┘
   提示词 + 启动配置      │ 内核 MCP（查记忆 / 查人 / 发消息）
         ▼               │
  CLI 适配器：Claude Code / Codex / Gemini / DSH ...
```

## 四个注入点

| 时机 | 注入什么 | 怎么注入 | 要 CLI 配合吗 |
|---|---|---|---|
| ① 启动会话 | 人格 | 翻译成各家原生的指令入口：Claude Code 用 CLAUDE.md 或 `--append-system-prompt`，Codex 用 AGENTS.md，Gemini 用 GEMINI.md | 每个 CLI 适配器写一份翻译 |
| ② 每轮发消息前 | 说话人是谁、召回的相关记忆、来自哪个渠道 | 内核把这些拼在发给 CLI 的提示词前面 | 不用，任何 CLI 都接收提示词 |
| ③ 对话中按需调用 | 深挖记忆、查某个人、主动给某人发消息 | 内核起一个 MCP server，启动会话时挂给 CLI | 主流 CLI 都支持 MCP |
| ④ 每轮结束后 | 写入记忆 | 内核本来就在转发 CLI 的输出，拿完整对话交给便宜模型异步抽取 | 不用 |

②和④是地基，因为它们不依赖 CLI 配合。③是增强，"主动找你"也走这条：agent 调用内核提供的 `send_message` 工具。

Paseo 自己的插件机制也开了类似的口子：改 agent 启动配置、环境变量、MCP 挂载、时间线，可以当参考。

## 两个坑要提前避开

1. **人格只能追加，不能覆盖。** CLI 自带的系统提示词里有"你是编程助手、工具怎么用"。整个替换掉，它会丢掉干活能力。CSDN 教程也提醒过，DSH 的 `complete: true` 会移除第一方工具引导。
2. **写记忆别指望 agent 自觉调用工具。** 模型经常忘。靠④在内核里抽取才稳定，MCP 写入只当补充。

第一期我仍建议上次的方案 A，只是"内核"的含义变了。现在第一期做的是：CLI 适配器、渠道适配器接口、上面四个注入点，加上电脑端。如果你想换别的顺序，直接说。

## 下一个问题：人格在不同场景下强度一样吗？

- **A**：全场景都是同一个大肥鱼，写代码时也傲娇，只调整回复长度。
- **B（我推荐）**：一个人格分两档。聊天渠道用完整人格；干活时切到"工作模式"，只保留称呼和语气，不加戏。
- **C**：每个渠道、每个群各配一套人格。

## Paseo 自己是怎么做的（文档里写明的）

- 上层统一契约是它自己定义的 `AgentClient` / `AgentSession`，在 `agent-sdk-types.ts` 里，不是 ACP。
- 下层分两类适配器：

  - **ACP 适配器**：只有 Copilot、Cursor、Kimi、Kiro、Trae，加一个"通用 ACP 适配器"，让用户自己配任意支持 ACP 的 CLI。
- 原因在 `agent-sdk-capabilities.md` 里：原生 SDK 能做的事比 ACP 多。

## 我们恰好需要这些"多出来"的能力

| 我们需要的 | 为什么需要 | 原生 SDK | ACP（按我了解的规范） |
|---|---|---|---|
| 追加人格提示词 | 人格只追加、不覆盖 | Claude SDK 有 `systemPrompt` 参数 | 新建会话只有工作目录和 MCP，没有标准字段 |

| 用量和花费 | 预算上限是我们定的兜底之一 | Claude SDK 的结果里带 usage 和 cost | 没有标准字段 |
| 回滚 | 出错能退回去 | Paseo 已经做了 rewind | 没有 |

如果上层用 ACP，这些能力只能塞进 ACP 的私有扩展字段 `_meta`。结果等于穿着 ACP 外壳的私有协议。而且从 Paseo 摘来的适配器实现的是它的 `AgentSession`，还得再转一道 ACP，变成两层翻译。ACP 规范这一两年在更新，写 spec 前我会对照最新版本再核实一遍。

## 注意力问题：一个她，多个分身

你说的场景是：派了 3 件活，每件都要设计、要审核，你同时还在跟她聊天。全塞进一个 agent 的话，上下文会被任务细节塞满，聊天和干活都会变差。解法是这样：

- **主意识**：对话里的她只做三件事：跟你聊天、接活、汇报。任务细节不进她的上下文。
- **分身**：每件活由一个分身去做，各自有独立的上下文，同时跑，互不干扰。分身就是她背后开的那些 CLI 会话。
- **她知道每个分身在干什么**：她手上有每件活的状态摘要。你问"那三件活怎么样了"，她答得上来。
- **需要你时会找你**：哪件活要你审核，她会在对话里告诉你，任务看板上那件活也会亮起来。
- **经历会汇回来**：分身做完后，过程写进操作日志，再沉淀成她的记忆。这样每件活都是"她"做过的事。

还要澄清一点：这里的"审核"是干活流程的一部分，就像需求要先过设计评审。它跟自主权限无关，"完全自主、事前不审批"这条不变。

### 2. 整体运转：一个本体，五个循环

```
           外面进来的消息（主控台 / 网页，以后 QQ、微信）    时钟（作息）
                          │                              │
                          ▼                              ▼
  ┌──────────────────────────────────────────────────────────────┐
  │                      操作日志（一切都先记下来）                  │
  └──────────────────────────────────────────────────────────────┘
        │ ① 消息循环          │ ② 干活循环          │ ⑤ 生活循环
        ▼                    ▼                    ▼
     主意识  ───派活（原话）──▶ 对话（分身 / 朋友）    主意识自己发起一轮
        │  ◀──进度摘要、找你审核──  │ 可再开子对话
        ▼                    ▼
   回复、主动发消息        设计 → 审 → 执行 → 验收
        │                    │
        └─────────┬──────────┘
                  ▼
     ③ 记忆循环：日志 → 抽取 → 入库 → 下一轮召回、注入
     ④ 成长循环：记忆和日志 → 成长提案 → 新版本人设（可查、可回滚）
```

| 循环 | 什么时候转 | 做什么 |
|---|---|---|
| ① 消息循环 | 有人说话时，实时 | 主意识决定是回复、派活，还是两者都做 |
| ② 干活循环 | 并行，每件活一个 | 对话按"设计 → 审设计 → 执行 → 验收"推进，进度汇报给主意识 |
| ③ 记忆循环 | 每轮结束后，加上每晚 | 从日志里抽取记忆、入库；下一轮按隐私规则召回，注入大脑 |
| ④ 成长循环 | 每晚或定期 | 从记忆和日志里提出"她最近变了什么"，生成新版本人设，可查可回滚 |
| ⑤ 生活循环 | 按作息 | 没人找她时，主意识自己发起一轮：主动关心、兑现承诺；第四版加上自己逛、自己学 |

### 3. 贯穿全局的五条原则

1. **一切都是事件，一切都进日志。** 日志是唯一的事实来源，记忆和成长都从日志里长出来。
2. **灵魂归本体，大脑可以换。** 人格、记忆、关系存在本体里，CLI 只负责思考和干活。
3. **每个数字生命只有一个主意识，对话可以有很多个。**
4. **所有能力都靠插件扩展**，分大脑、形态、能力三类，本体不用改。
5. **依赖只往一个方向走。** 每个模块的数据只归它自己，别的模块只能通过它的接口来拿。

| 分层 | `websocket-server.ts` 负责连接和握手，`session.ts` 负责每个连接的订阅，AgentManager 是状态的唯一来源，providers 做适配。但 `session.ts` 有 8808 行、`agent-manager.ts` 5425 行、`daemon-client.ts` 7142 行、`messages.ts` 7689 行，都是巨型文件 | Gateway 持有所有渠道连接；渠道插件只做适配，发消息工具和会话 key 由核心统一提供 | 模块边界要一开始就定死，避免 session 变成什么都管的大对象 |
| 信封 | 顶层只有 `hello`/`ping`/`pong`/`session`，其余都包在 `session` 里；请求带 `requestId`，订阅带 `subscriptionId`；新 RPC 用 `a.b.verb.request/.response` 命名，有限流式请求加 `.update` | `{type:"req",id,method,params}`、`{type:"res",id,ok,payload\|error{code,message,retryable,retryAfterMs}}`、`{type:"event",event,payload,seq,stateVersion}` | 采用 req/res/ev 三种信封，再借 Paseo 的点分命名 |
| 版本 | 整数协议版本。schema 只增不删，新功能用 `features` 能力位在一处判断，兼容垫片要打 `COMPAT(name)` 标签并写上删除日期。根本原因是 app 和 daemon 分开发版 | 整数版本，当前是 4；能力位用字符串协商；文档明说"某个 method 存在不足以证明支持" | 灵鲸由本体托管前端，前后端版本天然一致，可以省掉整套兼容矩阵 |
| 校验 | 用 zod 写 schema；schema 必须是纯结构声明（不许 transform/catch/preprocess），用 discriminatedUnion；客户端走 zod-aot 生成的校验器。在 Hermes 上实测，353KB 的消息校验从 10.9ms 降到 2.5ms | TypeBox 生成 JSON Schema，再生成 Swift 模型 | 用 zod 并守住"纯 schema"规则即可；zod-aot 还年轻，Paseo 要给它的编译器打补丁，等测出性能问题再上 |
| 同步 | 两条通路：实时流管"及时"，`fetch_timeline` 分页管"正确"。缺口靠向后分页追到 `hasNewer:false`；打开对话只取一页最新尾部；目录类数据每个实体一个单调序号，只保留最新投影和 tombstone，游标过期就给全量快照；只给打开着的对话推实时流 | seq 按连接单调递增；事件不重放，发现缺口就断开重连、拿快照；有副作用的方法必须带幂等 key | 采用"实时流不持久，按游标补齐，过期给快照" |
| 流式性能 | daemon 端按 agent 合并 delta，60ms 一帧，首个 delta 立即发、后续攒批；客户端每帧提交一次（隐藏标签页用定时器兜底）；展示时按积压量匀速吐字；Markdown 只重解析最后一个增长中的块。实测吐字中位间隔从 317ms 降到 17ms | 远程连接对 1KiB 以上的帧做 permessage-deflate，本机不压缩 | 前三条照抄 |
| 背压 | 每条物理 socket 有 8MiB 上限，超过直接断开这条 socket；终端只在 bufferedAmount 超过 4MB 时才退回快照；工具输出截到 64KiB。我 grep 没找到 permessage-deflate 配置（ws 库默认关闭） | 默认 maxPayload 25MiB；握手的 hello 自带快照 | 低带宽下要更激进：限制单帧大小，再压缩 |
| 存储 | 全部是 JSON 文件，写临时文件再 rename，没有迁移框架；时间线只放内存，持久的"真相"是 CLI 自己的会话记录（如 `~/.claude/projects/*.jsonl`） | node:sqlite | 灵鲸不能拿 CLI 的会话记录当真相（见 3.2） |
| 子进程 | `runtime/managed-processes/{id}.json` 记录本体拉起的进程，启动时对账清理 | — | 照抄这个思路 |

## 3. 对灵鲸的设计建议

### 3.1 进程模型与模块边界

**进程模型：** launchd 托管一个 Node 24 主进程（KeepAlive），外加以下子进程：
- 大脑 CLI：每个对话一个（Claude 用 Agent SDK 或 `claude -p --output-format stream-json`，Codex 用 `codex app-server` 的 stdio JSON-RPC）。
- 以后的 pty worker。

其他安排：
- 重查询（日志全文检索、每晚整理）放进 worker_threads，用独立的只读连接。
- 写操作留在主线程单写者。

理由：上游 Paseo 最新的主线就是"别阻塞事件循环"〔一手〕；node:sqlite 的 API 全是同步的〔一手〕。

| 模块 | 唯一职责 | 对外 API | 不得做的事 |
|---|---|---|---|
| `gateway` | HTTP 静态资源、WS 握手与鉴权、连接会话、订阅登记、背压、序列化 | 调用 commands/queries；订阅 projection 的变更流 | 不懂业务规则 |
| `journal` | 只追加的操作日志，单写者；分配 `pos` 和流内 `seq`；在同一事务里跑内联投影；把提交后的事件发到进程内总线 | `append(stream, expectedSeq, events)`、`read(from)` | 不被其他模块直接查表 |
| `projections` | 看板、对话列表、时间线、花费、成员状态这些读模型 | 查询接口加变更流 | — |
| `tasks` | 任务状态机与关口（设计中、等你审设计、执行中、等你验收、完成，另有暂停、叫停、失败） | `submitDesign`、`approveDesign`、`requestChanges`、`accept`、`reject` | 不跑大脑 |
| `conversations` | 对话、分身、子对话的归属树，轮次管理，大脑绑定 | `send`、`pause`、`stop`、`switchBrain` | — |
| `mind` | 主意识：判断"这是不是活、交给谁"，把原话加记忆派下去，汇报进度 | 只订阅里程碑事件 | 不接收分身的 token 流（保护注意力） |
| `brains` | CLI 适配器：归一成 BrainEvent（text.delta、tool.start/update/end、permission、usage、turn.end、error）；备用大脑切换 | — | — |
| `procs` | 进程组 spawn 与杀整棵进程树、超时、看门狗；进程登记表持久化，启动时对账 | — | — |
| `workspace` | 文件树、读写、git status 与 diff（本体算）、改动前快照、回收站 | — | — |
| `scheduler` | 持久化定时器表（作息、提醒、承诺、每晚整理），cron 表达式用 croner；重启后按策略补跑错过的 | — | — |
| `memory` / `persona` | 记忆和人格都是日志的异步投影；成长与人格变化带版本，可回滚 | — | — |
| `guard` | 花钱总闸、一键暂停、按类别收回能力 | 大脑每轮启动前必须问它 | — |
| `notify` | 注意力事件按在线状态路由给客户端，第二版再接 QQ/微信 | — | — |

依赖只能单向：gateway → 应用服务 → 领域模块 → journal。领域模块之间只走公开 API 或日志事件，各自拥有自己的表。

### 3.2 操作日志与投影

**核心取舍：** Paseo 的时间线只放内存，持久的真相是 CLI 自己的会话记录〔一手〕。这和"灵魂归本体、换了 CLI 她还是她"冲突。所以灵鲸要自己持有规范时间线：操作日志是真相，CLI 的会话记录只是 resume 用的缓存。

**表结构：** `events(pos PK, stream_type, stream_id, stream_seq, type, v, actor, occurred_at, causation_id, correlation_id, provenance JSON, payload JSON, UNIQUE(stream_id, stream_seq))`。
- `provenance`（场合、参与者、可见性）第一版就写进去。"隐私按来源"和"记忆来源"都靠它，现在加几乎没有成本，以后补要做迁移。

**两类事件：**
- 持久事件：消息完成、工具调用完成（输出有上限）、阶段流转、用量记录、快照、记忆增删改。
- 临时流事件：token delta、工具进度。不入日志，在条目边界（一条消息或一次工具调用结束）提交。
- 崩溃时，有 `turn.started` 没有结束的轮次，启动时补一条 `turn.interrupted`。

**大对象：** 工具输出、diff、图片、语音存成按哈希寻址的文件，事件里只放引用。

**投影：**
- 内联投影（同一事务）只给界面强依赖的几张表：看板、对话列表、时间线、花费汇总。Emmett 作者提醒过内联投影会拖慢追加〔二手〕。
- 记忆抽取、全文检索、成长日记走带检查点的异步投影。
- 要能删掉投影表、从日志重放重建，这同时就是迁移手段。
- 单用户规模不需要快照。

**备份：** node:sqlite 的 `backup()`〔一手〕加上 blob 目录。

### 3.3 协议草案

```
C→S {t:"hello", protocol:1, build, client:{kind:"console"|"web"}, auth, resume:[{topic,cursor}]}
S→C {t:"welcome", protocol:1, build, features:[], limits:{maxFrame:262144}}
C→S {t:"req", id, m:"task.approve_design.request", p:{taskId}, idem}
S→C {t:"res", id, ok:true, p} | {t:"res", id, ok:false, e:{code,msg,retryable,retryAfterMs}}
C→S {t:"req", m:"sub.open.request", p:{topic:"conversation:abc", cursor}}  → res 带快照或增量，以及 subId
S→C {t:"ev", sub, seq, k:"timeline.item_committed", p}
```

**事件分类：**
1. 实体：`entity.upsert` / `entity.remove`，带实体版本，只同步最新状态（Paseo directory-sync 的做法）。
2. 时间线：已提交的条目，带 `(conv, seq)`，可分页 `timeline.fetch before/after`。
3. 实时流：`stream.delta {item, offset, text}`，不重放，靠偏移量去重。
4. 注意力：审设计、验收、出错、关心。
5. 系统：健康状况、暂停状态、花费状态、心跳。
6. 终端：以后用二进制帧。

**版本策略：**
- 主控台和网页都由本体托管，前后端同版本发布。
- `protocol` 或 `build` 不一致时，客户端只提示"本体已更新，刷新一下"，不做兼容。
- 照样守住三条成本很低的规则：schema 只增不删；schema 保持纯结构；用 discriminatedUnion。这样第五版手机端独立发版时，再引入能力位也来得及。
- 有副作用的请求一律带幂等 key（OpenClaw 和 Paseo 都这么做）。

### 3.4 低带宽（&lt;70KB/s）下的同步

1. **先排查链路。** Tailscale 官方说 DERP 中继本身会限流，性能差最常见的原因是没打通直连。先用 `tailscale status` 和 `tailscale netcheck` 看是否直连，打不通可以考虑 peer relay〔二手〕。
2. **静态资源。** 文件名带内容哈希，`Cache-Control: immutable`，预压缩 brotli（Paseo 的 `web-ui.ts` 已经这么做）。编辑器、diff、终端按需懒加载。
3. **WS 压缩。** 非本机连接开 permessage-deflate，阈值 1KiB（OpenClaw 的做法）。
4. **按需推送。** 只有正在看的对话推 token；其他并行的活只推看板实体变更（阶段、摘要、注意力）。
5. **合并与降级。** 每个对话 60–100ms 合并一帧；bufferedAmount 超过阈值时，这个对话降级为只推"条目完成"。
6. **限制大小。** 单帧 ≤256KB；工具输出截断，全文按需取；diff 先发文件清单和统计，每个文件的 hunk 打开时再取。
7. **断线续传。** 重连时在 hello 里带上各 topic 的游标。时间线只补一页最新尾部，更早的随滚动加载；游标过期就给快照。
8. **本地缓存。** 客户端用 IndexedDB 存已提交的条目，先画缓存再对账（Paseo replica-cache 的思路）。
9. **大文件。** 图片、语音、文件走 HTTP GET 加 Range 加缓存，不塞进 WS 的 base64。

### 3.5 前端工程结构与状态

**包结构：**
- `packages/protocol`：zod schema 与类型。
- `packages/client`：连接、req/res、订阅管理器（游标、重订阅、1s→30s 指数退避）、合并后的流事件 API。
- `packages/core`：本体。
- `packages/ui`：Vite 加 React。
- `packages/desktop`：以后再加。

**状态分四类：**
1. 服务端副本：zustand vanilla store，由 client 包的订阅回调写入，不经过 React effect。
2. 请求型数据（文件内容、diff、日志检索）：TanStack Query，收到 fs/git 事件后失效。
3. 流式文本：每个对话一块"实时头"缓冲，每帧提交一次，匀速吐字，Markdown 只重解析最后一块。照抄 Paseo 的不变量。
4. 界面本地状态（布局、草稿、展开的目录）：按对话 id 归属，持久化到本地。按 Paseo 的规则区分"目录共享"和"对话自有"两类 key。

**桌面能力：** 界面里定义一个 `HostBridge` 接口，提供 web 和 Electron 两种实现（Paseo 的 `window.paseoDesktop` 是同一思路）。

### 3.6 主控台信息架构

**顶栏：** 她的头像和当下状态（心情、在忙什么）、花费仪表、一键暂停、注意力铃铛。

**左侧导航：** 她（首页）、任务、工作区、成员、日志与花费、设置。

**首页：**
- 中间是和主意识的对话。
- 右侧是"她手上的事"：按阶段分组的小卡片，"等你审设计"和"等你验收"带数字徽标。
- 主意识派活、汇报时，在消息里插入任务引用卡，点开直达这件活。

**任务页：**
- 五列看板加顶部一条"需要你"泳道。
- 卡片显示标题、执行者（分身还是朋友）、大脑、耗时、花费，以及分身写的最新一句进度摘要。不显示 token 流。
- 阶段流转只用明确的按钮（批准设计、打回修改、验收通过、打回），不支持拖拽。理由：审核是带语义的命令，拖拽容易误批。Vibe Kanban 就是拖卡片即启动 agent。
- 任务完成时不抢焦点（Cursor 论坛有用户专门抱怨过这一点〔二手〕）。

**任务详情（就是这件活的对话本身）：**
- 左栏：阶段时间线、设计文档（Markdown，可以加批注）。

### 3.7 第一版客户端：网页优先，Electron 以后作为薄壳加入

依据：
1. **省掉版本兼容。** Paseo 的兼容负担来自 app 和 daemon 分开发版〔一手〕。由本体托管的网页天然同版本；而 Helm 的 Electron 把前端打进包里〔一手〕，会重新带来版本错开。
2. **签名与更新。** 没有 Developer ID，macOS 自动更新就卡在签名上〔二手〕；网页完全没有这个问题。
3. **第一版的需求网页都能覆盖。** 唯一的短板是"电脑通知"。注意：浏览器的 Notification 和 Service Worker 都要求安全上下文，`http://100.x` 这种 tailnet 地址不算〔Web 平台规则〕，所以要用 Tailscale Serve 提供 HTTPS，或者在本机走 localhost。另外标签页关闭后就收不到通知。
4. **Electron 的独有价值在后面的版本。** 托盘、常驻通知、开机自启、全局快捷键（第一版可做可不做）；看主人屏幕需要 desktopCapturer（第四版）；桌宠需要透明置顶窗口（第五版）。

建议：第一版的后期里程碑如果需要可靠通知，就加一个约 300 行的薄壳。
- 壳直接加载本体的 URL，只暴露托盘、通知、自启、快捷键四个白名单 IPC，并校验 sender 来源。
- 打开 Electron Fuses（关闭 RunAsNode 等）。
- 不做自动更新：前端在本体侧更新，壳本身几乎不用变。

## 4. 坑与反例

1. **兼容性让复杂度失控。** `timeline-sync.md` 有 20KB，几乎全是边界情况〔一手〕。同版本发布能直接避开。
2. **node:sqlite 的版本坑。** 24.15.0 之前的版本 TEXT 遇到内嵌 NUL 会被静默截断，24.16.0 修复；WAL 重置损坏要求 SQLite ≥3.51.3。OpenClaw 因此要求 Node ≥24.22.1，并在启动时自检〔一手〕。建议照做：启动时检查 `sqlite_version()` 和 NUL 往返。
3. **同步 API 堵主线程。** 长查询会卡住事件循环；单个 250KB 的消息会让终端回显掉帧约 100ms〔一手，Paseo 实测〕。
4. **不要用心跳决定是否投递。** Paseo 明确禁止〔一手〕。
5. **OpenClaw 默认值不适合慢链路。** hello 自带快照、maxPayload 25MiB、超过 2 倍 tick 静默就断开，都要调大或裁剪〔一手〕。
6. **Electron 的两个坑。** 通用 invoke 不校验 sender；preload 里 require 本地模块会在沙箱下中断〔一手〕。
7. **孤儿进程。** 大脑 CLI 在本体崩溃后会成为孤儿。要 detached 启动，按负 pid 杀整个进程组，并在启动时对账。
8. **Vibe Kanban 已宣布停止运营（2026-04-10）。** 原因是商业模式，不是产品本身〔一手〕。对自托管的灵鲸没有直接影响，但提醒一点：看板不该成为唯一主轴，灵鲸的主轴是"她"。
9. **Codex app-server 的 WebSocket 传输还是实验性的**，生产用 stdio〔二手〕。
