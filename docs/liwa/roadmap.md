# liwa 实现步骤

日期 2026-11-16 · 状态：现行（分期主人 2026-11-15 确认；排期 2026-11-16 写成，待主人审）。

产品定义以 [`product.md`](product.md) 为准，这里只写**怎么分期做、每期动工前要先定什么、怎么算做完**。依据的代码版本：`develop@940c633c`（上游 Paseo 0.16.0 加 liwa 的提交）。标记：〔一手〕源码直接可见；〔推理〕自己推出来的。

## 0. 结论

- **分五期，每期都是一个独立的子项目**，按顺序做：记忆库 → 双层 → 角色与群 → 数字生命 → 外部适配器。每期各走一轮"设计 → 主人确认 → 详细计划 → 实现 → 验收"，前一期验收完再动下一期的代码。下一期的设计可以提前写。
- **能做成插件的就做成插件，必须改 Paseo 核心的才改核心。** 记忆库、角色的人设注入基本能做成 liwa 内置插件；双层和群要改核心。这样以后合上游 Paseo 时冲突最少。
- **双层是最大的一期**，它的设计已经审过五轮，要按新的产品模型改一遍再动工。
- **第一版功能优先，界面够用就行。** 主人 2026-11-15 定：各期先把功能做出来，界面用 Paseo 现有的部件拼到能用为止，不做视觉和交互上的打磨；五期功能都做完后，再统一打磨一轮界面。标准见第 1 节末尾。
- **排期**：五期计划在 2027-03-19 前后做完，之后统一打磨界面；每期的起止日期见第 2 节。第 1 期设计稿已写好，等主人确认后开工。

## 1. 每一期都按这个流程走

| 步         | 做什么                                                                                                              | 产出                          | 谁定                                                         |
| ---------- | ------------------------------------------------------------------------------------------------------------------- | ----------------------------- | ------------------------------------------------------------ |
| 1 设计     | 写清这一期的范围、模块划分、数据放在哪、对 Paseo 改哪里、错误怎么恢复、怎么验证（测试分几层、验收场景、什么算做完） | `docs/liwa/` 下这一期的设计稿 | agent 写，主人确认；双层这种大设计，确认前可以加一轮独立审核 |
| 2 详细计划 | 把设计拆成逐个任务，每个任务写清改哪些文件、先写什么测试、怎么跑                                                    | 详细计划                      | 主人过目                                                     |
| 3 实现     | 从 `develop` 拉功能分支，一个任务一个任务做，每个任务先写测试；可以交给子 agent 并行，逐个审                        | 功能分支上的提交              | —                                                            |
| 4 合回     | 格式、lint、类型检查、改到的包的单测全部通过；审完快进合回 `develop`                                                | `develop` 上的提交            | —                                                            |
| 5 验收     | 照设计稿里的验收场景，在开发版上实际用一遍；主人试用                                                                | 验收记录                      | 主人                                                         |
| 6 发版     | 验收通过后把 `release` 跟到 `develop`；评估要不要合一次上游 Paseo                                                   | `release`                     | 主人                                                         |

**所有期都遵守的规则**（详见根目录 `CLAUDE.md` 开头的 liwa 一节）：

- liwa 新代码放在新目录或插件里；改 Paseo 原有代码只通过公共契约改，并为每处改动写契约测试。
- 跑开发脚本和测试前，先去掉继承的 `PASEO_HOME` 等变量；Node 用 22.20.0。
- 文档只存最新方案；每期的设计稿写进 `docs/liwa/`。
- 新界面先保证桌面和网页能用，手机端随后跟上（[`product.md`](product.md) 第 11 节第 8 条）。

**界面够用的标准**：每个新界面只要求三件事：需要的信息看得到、需要的操作做得了、出错有提示。做法是复用 Paseo 现有的部件（列表、表单、右侧面板、设置页、对话时间线），不做专门的视觉设计、动效、插画和新手引导，手机端第一版不专门适配。各期的界面做到下面这样就够：

| 期  | 界面做到这样就够                                                                                                                                                                  |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 设置里一页"记忆"：表格列出每条的内容、范围、受众、来源、状态；每行能删除，待确认的有"确认 / 丢弃"两个按钮                                                                         |
| 2   | 主对话就是普通对话页；右侧面板一个工单列表（标题、阶段、执行者、最近回报），点一行打开执行器对话，处置按钮直接放在行上；健康板是设置里的一个列表；新建 agent 时有一个"双层"勾选框 |
| 3   | 角色库是设置里的列表加编辑表单；群对话复用现有的对话时间线，每条消息前显示发言人；群成员是右侧面板里的一个列表；@ 成员先支持在输入框里直接打"@名字"，补全以后再做                 |
| 4   | 她的页面是设置里的几个列表：人设版本（当前的、待确认的，带确认按钮）、人物级记忆、成长记录                                                                                        |
| 5   | "空间与人物"是设置里的一张绑定表；适配器自己的界面用插件平台现成的设置页                                                                                                          |

## 5. 第 2 期：双层模式

**范围**（[`product.md`](product.md) 第 4.2、4.3 节）：主对话只有对话和派活的工具；工单账本只由代码写；名额和排队；回报带证据；主人说"可以了"才结单；工单栏；主人直接找执行器追加；高危权限只转告；重启后结果不明在工单栏处置；停止只停当前一轮；健康板；"转给主对话"；匿名执行器和执行配置；模式切换（换新会话）。

**落点**：要改核心。

- 新代码放 `packages/server/src/server/layer2/` 和 `packages/protocol/src/layer2.ts`。
- 对 Paseo 原有代码只改公共契约：创建、投递准入、控制入口、角色的工具策略、MCP 身份、恢复、时间线投影、配置、启停、worktree 准备、权限答复等。之前的设计列过 16 条。
- 工单栏、健康板是客户端的内置界面。

**设计依据**：之前有一份在 Paseo 上做的双层设计稿（不在本仓库），审过五轮。它是这一期的起点，但要按新的产品模型改：

| 要改的            | 为什么                                                                                                                              |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 主对话接入记忆库  | 第 1 期之后，主对话和执行器都要带系统级记忆                                                                                         |
| 模式切换          | 新模型里每个 agent 都能在普通和双层之间换，切换就是换新会话                                                                         |
| 给第 3 期留口子   | 执行者以后可以是角色，要有可派名单；工单要能记"指定给哪个角色"                                                                      |
| 运行环境          | 旧稿按 Node 24 写，Paseo 钉的是 22.20.0（`.tool-versions`〔一手〕）；账本用 SQLite 的话，要和第 1 期一起确认 `node:sqlite` 能不能用 |
| 第五轮剩下的 3 处 | 原稿里已经改了，但还没复核                                                                                                          |
| 名字对齐          | 主会话叫"主对话"，和产品文档一致                                                                                                    |

**设计稿要先定的问题**：哪些提供方能当主对话（要能在创建时把读写代码的工具收掉；旧稿有一张各家能力的对照表，要按 Paseo 现在的版本重新核实）；账本的存储和恢复；名额默认值。

**怎么算做完**：这些场景全部走通：派工到结单、问进度、直接找执行器追加、高危权限、重启后结果不明的处置、名额满了排队、普通模式和双层模式来回切换；连续用一周，没有一件活丢失、重复执行，或者结果说不清。

**做完之后**：用 liwa 替换主人日常用的 Paseo.app，只改应用的显示名和图标（[`product.md`](product.md) 第 11 节第 9 条）。liwa 的数据目录和 Paseo 一样，换装后原来的数据照常可用；换装前先备份 `~/.paseo`。

## 6. 第 3 期：角色与群

**先做角色，再做群；群里先做直接 @，再做群里的调度。**

| 部分         | 范围                                                                                                                        | 落点                                                                                                                                                                                                               |
| ------------ | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 角色库       | 角色：名字、性格和职责、默认大脑、能不能被派活、最多同时几单；新建 agent 时选类型；人设放在系统提示最前面                   | 存储和角色库页面做成插件；人设靠 `agent.create.before` 注入〔推理：同第 1 期〕。Paseo 已有的 agent 配置档案故意不带系统提示（`agent-profile.ts:8-10`〔一手〕），所以角色不能直接塞进档案，要另存，开会话时再拼进去 |
| 角色当执行器 | 双层 agent 的可派名单；开单时指定角色；同一角色可以同时接多单                                                               | 核心：第 2 期的账本和派单                                                                                                                                                                                          |
| 群：直接 @   | 群容器、成员名单、群消息只存一份、唤醒门（被 @、被回复才叫醒）、每个成员在群里一个自己的 worktree、成本闸、群对话和群成员栏 | 核心：群消息和唤醒规则；客户端：群界面                                                                                                                                                                             |
| 群：调度     | 一个群最多一个双层 agent 当调度；没 @ 任何人的话交给它；它只派给群成员和匿名执行器；被派成员的提问和结果署名发到群里        | 核心：在第 2 期的账本上加"在哪个群开的、派给谁"                                                                                                                                                                    |

**设计稿要先定的问题**：群消息怎么分批投进每个成员的会话；成员在群里的 worktree 怎么建、怎么回收；成本闸的默认值；没有调度的群里没人被 @ 时，默认成员怎么设。

**怎么算做完**：@ 一个人只叫醒这一个；没人被点不花钱；有调度的群里从派活到结单走通；角色能被私聊里的双层 agent 和群里的调度派活；连续用一周，没有成员抢活、两个成员同时改同一个目录，或者谁说的话分不清。

## 7. 第 4 期：数字生命第一版

**范围**（[`product.md`](product.md) 第 5.1 节）：

- 人设与出生设定；人物级记忆，受众由代码按来源和在场的人盖章；
- 成长：夜里整理经历，提出人设新版本，主人确认后在下一个新会话生效，可以撤回；
- 经历流；人与账号绑定（先只做"人"和"主人"）；到点主动开口；闲聊；
- 她在任何位置都带着同一份人设和记忆；"她的页面"。

**落点**：

- 新建成员数据模块，存人设版本、经历流、成长记录；代码只经它的接口读写。
- 人物级记忆存在第 1 期的记忆库里，是一种新范围，不另起一套。
- 定时开口由 liwa 自己的定时器往指定对话里记一条触发。Paseo 自带的定时是新建 agent 或往同一个对话回灌，和这里要的不一样〔推理，依据旧整体架构页的核对〕。

**设计稿要先定的问题**：受众盖章的规则（来自哪个对话、当时谁在场）；成长流程怎么跑、提案长什么样；"换大脑还是她"的固定问答怎么出、怎么比；闲聊不能夹带工单结果怎么检查。

**怎么算做完**：[`product.md`](product.md) 第 5.1 节的验收表：接得上、隐私不漏、不编造、换大脑还是她、成长看得懂、不操纵。
